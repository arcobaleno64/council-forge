## Scope

TASK-1008 Assurance Strict/Legacy + Schema Clarification: codification of the assurance level vocabulary, strict/legacy validation split, and resolver pipeline documentation.

## Issue

The governance repair plan v3.4 §4.3 identifies four policy gaps that must be closed before downstream repair tasks:

1. **`high` is used in some historical contexts** as an assurance level, but was never formally defined and conflicts with the three-level schema (`poc`/`mvp`/`production`).
2. **`normalize_assurance_level` silently defaults** unknown values to `poc`, making invalid assurance levels invisible to operators and validators.
3. **No mismatch check** exists between the `assurance_level` declared in task.md and in status.json; they can diverge silently.
4. **The resolver pipeline** (assurance baseline → adapter override → resolved policy) is implemented in code but not documented in `docs/artifact_schema.md`, making it hard to audit or reference.

## Options Considered

### Option A: Strict-only (no legacy mode)
Remove `normalize_assurance_level`'s silent default entirely; all artifacts must use exact vocabulary.
- Pro: Maximum strictness; no ambiguity.
- Con: Breaks downstream compatibility for historical artifacts that may have unresolved assurance values.

### Option B: Strict root mode + explicit legacy compatibility path (chosen)
Keep `normalize_assurance_level` for internal policy resolution (it's already called inside `resolve_verification_policy`). Add `validate_assurance_level_strict` (raises ValueError on unknown) and `warn_and_default_assurance_level` (explicit opt-in legacy mode). Change validation entry points to use strict checking.
- Pro: Backward-safe for internal resolution; legacy mode is explicit and auditable.
- Con: Slightly more surface area (two new functions).

### Option C: Feature flag
Add a `STRICT_ASSURANCE=True` global flag to toggle behavior.
- Con: Flag state is implicit and hard to audit; violates the "explicit authorization" requirement.

## Chosen Option

**Option B**: Strict root mode + explicit legacy compatibility path.

## Reasoning

### Why `high` is not a valid assurance level

The three-level schema (`poc` / `mvp` / `production`) maps to distinct governance artifact requirements defined in `ASSURANCE_PROFILES`. `high` has no corresponding profile, no defined required_artifacts_by_state, and no defined verify_required_sections. Any validator that encounters `high` cannot resolve a policy and must fail. Adding `high` as a fourth level would require a full profile definition and a decision artifact; absent that, `high` is a schema error.

### Why root strict mode rejects unknown assurance

Silent defaults corrupt the audit trail. When `normalize_assurance_level('high')` returns `'poc'`, the artifact appears to be a poc-grade artifact. Validators, reviewers, and downstream tasks all see `poc`—not the original intent. This makes any maturity assessment unreliable. The strict mode change converts this invisible corruption into an explicit error that must be resolved before the task can proceed.

### Why legacy mode may exist only as an explicit compatibility path

The v3.4 plan §4.6d (TASK-1015) will enforce strict verify floors across the full repo. Until then, historical artifacts that predate the strict mode must be accommodated without silent corruption. The legacy compatibility function `warn_and_default_assurance_level` records `defaulted_from`, `selected_default`, and `migration_debt` in a structured dict that is visible to any caller. This makes the compatibility path auditable and machine-readable; it cannot be silently activated.

### Why TASK-964 historical drill is not production maturity

TASK-964 was produced under a lower evidence floor (no structured checklist, no deterministic timestamps, no reviewer attestation). The conclusion of the drill may have been correct, but the evidence did not meet production-grade standards at time of production, and retroactive evidence repair cannot change what was attested at that time. Upgrading TASK-964 to `production` maturity would misrepresent the historical record and undermine the trust chain for downstream tasks that rely on TASK-964 as a reference point. TASK-1010 (Prompt 4) owns the production canonical drill.

## Implications

- All new and modified artifacts must declare `assurance_level` explicitly in both task.md (`## Assurance Level` section) and status.json (`assurance_level` field).
- Any artifact with `assurance_level: high` must be reclassified before the next validator run.
- `warn_and_default_assurance_level` may only be called from an explicit compatibility migration path, not from the normal validation flow.
- `docs/artifact_schema.md` §5.11 is the authoritative reference for the resolver pipeline. Validators must not re-derive policy from artifact heuristics.
- TASK-964 remains permanently at `mvp + limited evidence`.
