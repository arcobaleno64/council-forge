## Issue

v3.4 §4.6a requires a verify evidence floor policy with two tiers:
1. Historical unchanged verify artifacts → advisory until Prompt 6d enforcement
2. New or modified verify artifacts after baseline → strict immediately

Three design decisions were required:
- How to identify "historical" vs "post-baseline" verify artifacts deterministically
- How to record TASK-964 limited evidence as baseline-known debt without inflating its status
- Whether to enforce strict policy now or only in dry-run mode

## Chosen Option

**SHA256-based baseline manifest with dry-run targeted enforcement.**

- `artifacts/governance/verify-floor-baseline.v3.4.json` snapshots all 32 existing verify artifacts with their SHA256 at baseline time.
- Any verify artifact not in the baseline, or whose SHA256 has changed from the baseline record, is classified as `strict`.
- Baseline entries retain `floor_status = "advisory_until_6d"` until TASK-1015 (Prompt 6d) runs full enforcement.
- TASK-964 receives `baseline_known_debt = "limited_evidence"` in its entry — this documents the known debt but does NOT change its evidence or maturity.
- `--verify-floor-dry-run` flag in guard_status_validator.py enables targeted policy classification without global enforcement.

## Reasoning

**SHA256 is deterministic and tamper-evident**: it captures exact file content at baseline time, making any subsequent modification detectable. A content hash is more reliable than timestamps, which can be manipulated or vary by clock.

**Dry-run mode is required**: full repo enforcement is explicitly deferred to Prompt 6d / TASK-1015 per the v3.4 plan execution order. Enforcing strict mode now on all 32 historical verify artifacts would block the workflow, which contradicts the advisory_until_6d policy.

**TASK-964 baseline_known_debt**: recording it in the baseline manifest makes the limited evidence debt visible and traceable. It does not change TASK-964.verify.md content — only annotates the baseline entry.

**Rejected alternative — timestamp-based baseline**: file timestamps are non-deterministic (git checkout resets mtime), making SHA256 strictly superior.

**Rejected alternative — immediate strict enforcement**: would require fixing all 32 historical verify artifacts before this task can complete, which contradicts the phased approach defined in v3.4.

**Rejected alternative — "all current" baseline semantics**: including `artifacts/verify/TASK-1009.verify.md` in `baseline_verify_files` was explicitly rejected. The baseline is a snapshot of artifacts that existed **before** TASK-1009 created its own verify artifact. Including TASK-1009.verify.md would incorrectly classify it as `advisory_until_6d` instead of `strict`, undermining the post-baseline strict policy. The correct baseline count is 32 (pre-TASK-1009). The current total count after TASK-1009 completion is 33. This divergence is correct and expected: every new verify artifact after the baseline is `strict` by policy.
