## Issue

`run_red_team_suite.py` 的 `run_command` 使用 `subprocess.run(..., capture_output=True)` 無 timeout 保護。若被測 subprocess 掛住，整個 suite 卡死，無法產生任何 FAIL 結果。需決定 timeout 機制、sentinel returncode、output cap 策略。

## Options Considered

### Option A：subprocess.run(..., timeout=N)
- 優點：API 簡單，單行修改
- 缺點：timeout 後子 process 未被 kill，仍可能消耗資源；`subprocess.run` 內部 communicate() 不能在 timeout 後 drain buffer

### Option B：subprocess.Popen + communicate(timeout=N) + kill()
- 優點：Python 官方文件的標準 timeout cleanup idiom；timeout 後 kill()，再次 communicate() drain buffer；子 process 完全終止
- 缺點：程式碼略多（約 20 行替換 1 行），但清晰可審計

### Option C：threading.Timer + kill()
- 優點：更大的彈性
- 缺點：複雜度遠超需求；Popen.communicate(timeout=) 已足夠

## Chosen Option

**Option B**：subprocess.Popen + communicate(timeout=N) + kill()

## Reasoning

Option B 是 Python 官方建議的 timeout 處理 idiom（subprocess 文件中明確列出）。kill() 後再次 communicate() 確保子 process 完全終止且 buffer 被 drain。Option A 的 subprocess.run(timeout=) 在 timeout 後不 kill 子 process，違反 "hung process 必須可被終止" 的要求。

## Implications

- TIMEOUT_RETURNCODE = -9999 選為 sentinel：與實際 exit code 0/1/-1/42 等完全不重疊
- EXCEPTION_RETURNCODE = -9998 區分 OS 層級的非預期 exception（FileNotFoundError 等）
- build_case_result 比較 returncode == expected_exit_code 自然使 TIMEOUT/EXCEPTION 案例回傳 passed=False，不誤判為 pass
- output cap（MAX_SUBPROCESS_OUTPUT_BYTES = 1 MiB）為後置截斷（post-hoc）：讀取完整 output 後截斷；防止下游處理大量資料，但不防止 subprocess 在 Popen 期間產生超量 output 消耗記憶體。這在 TASK-1014 scope 內已足夠；stream-level interception 屬更複雜的後續工作。
- 不在 STATIC_CASES / LIVE_CASES / PROMPT_CASES 加入 timeout smoke case：smoke test 作為驗證工具，不得 promotion 為 regression result（Prompt 6e / TASK-1019 的職責）。
