## Reasoning

1. **artifact-first 原則之精神**：「不依賴 memory」之核心是「artifact 為單一權威」。若 user 提供 v3.3 之十一項缺陷描述為事實基準，且 v3.4 plan 顯式記載這些缺陷與其修復策略，則 v3.4 plan 本身即成為新的 artifact 基線；v3.3 是否曾落為檔案，於後續流程已無 operational 意義。
2. **artifact-first 失敗模式之自證**：v3.3 缺檔本身即 v3.4 所欲修復之治理失敗（「governance plan first, artifacts later」）之最強證據；此 decision 即為「artifact-first 不可逆轉」之第一個顯式落地。
3. **Option A 風險**：拒絕執行將使治理修復永久 stuck；user 已於 prompt 顯式接受「v3.4 為新檔，不直接編輯 v3.3」，故不視為阻塞前提。
4. **Option B 風險**：偽造 placeholder 違反 [CLAUDE.md](../../CLAUDE.md) §「不依賴 memory」與 §「artifact 為下一個代理的可用契約」；後續代理讀此 placeholder 將以為 v3.3 內容為何，引發更深誤解。
5. **Option D 風險**：失去 supersession 語義將使 v3.4 之 §「v3.3 已知缺陷」成為孤立散文，後續代理無從理解修復鏈之因果。

**雙標 Decision Class 之合理性**：

- frontmatter 之 `governance-plan-supersession` 為 v3.4 引入之新 taxonomy，記入 frontmatter 以保留 future validator 升級之 forward compatibility。
- markdown body 之 `conflict-resolution` 為現行 [docs/artifact_schema.md](../../docs/artifact_schema.md) §5.7 所容之固定 taxonomy；保留此值使現行 [guard_status_validator.py](../../artifacts/scripts/guard_status_validator.py) 與 [guard_contract_validator.py](../../artifacts/scripts/guard_contract_validator.py) 不會因 unknown class 而 fail。
- 本 plan §Risks R3 已記載此雙標策略之未來相容風險與 mitigation。
