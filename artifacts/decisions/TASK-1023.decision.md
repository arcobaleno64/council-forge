## Issue

User 於 2026-05-04 提出 Prompt -1（v3.5.0 Quality Control Surface Lifecycle），要求以 artifact-first lifecycle 建立 v3.5.0 治理品質控制面，作為 v3.4 治理修復計畫之**補強**（builds on）而**非取代**（not supersedes）。User prompt 列舉 v3.5.0 須處理之五項治理需求：

1. **FIND-29 source/template sync fragility**：v3.4 之 source/template pair 仍仰賴人工 `template/` 同步，缺少 baseline-aware exact-sync 與 drift waiver expiration。
2. **FIND-30 validator and test monolith maintainability risk**：`artifacts/scripts/guard_status_validator.py` 與其 unit tests 已長至單檔 monolith；refactor 風險高，須先量測 baseline 再決定是否拆檔。
3. **FIND-31 multi-model style and behavior drift**：Claude / Codex / Gemini 之 style、CLI 輸出、JSON schema、import-time side effect 缺乏跨模型一致性 gate。
4. **FIND-32 cross-artifact consistency blind spot**：v3.4 之 verify floor 與 contract validator 為單 artifact 等級；缺少 pre-commit cross-artifact 結構一致性檢查（PCACC）。
5. **FIND-33 artifact obligation ambiguity**：v3.4 對「該 task 該不該有 X artifact」採隱性慣例；缺少 obligation matrix 約束。

**關鍵衝突 1（v3.4 vs v3.5 關係）**：v3.4 治理修復鏈已封閉（TASK-1016 done，commit `2403c98`）。v3.5.0 之引入若處理不當，可能被誤讀為 v3.4 之 supersession，造成 v3.4 evidence chain 被誤標 superseded，破壞 audit trail。User prompt 顯式要求 v3.5.0 為 `builds_on` 而**非** `supersedes`；本決策必須在文字、metadata、manifest 三層同步落實此關係。

**關鍵衝突 2（artifact-first vs 生產壓力）**：v3.4 已修復「先計畫後 artifact」之 zombie 失敗模式。v3.5.0 之 prompt -1 顯式警示「不得復發」；本任務必須先建立 TASK-1023 lifecycle artifacts 後才能寫 v3.5 plan / manifest，**不可** 倒序。

**關鍵衝突 3（control surface vs refactor）**：FIND-30 暗示 validator 拆檔，但 prompt -1 顯式拒絕在 v3.5.0 啟動真拆檔；validator split 屬 v3.5.1 / v3.6 候選。本決策須在 v3.5 plan 明示「v3.5.0 = controls before refactor」之 version split rule，避免後續代理把 baseline metrics 當成拆檔授權。

**關鍵衝突 4（PCACC vs reasoning audit）**：FIND-32 之 PCACC 容易被誤解為「reasoning faithfulness audit」或「belief-state audit」；prompt -1 顯式排除這些，要求 PCACC 僅做四條結構性 checks（lifecycle artifact set、evidence refs format、canonical owner/reviewer、review timestamp ordering），且輸出必須為 JSON only、status 限三值（`pass`/`fail`/`skipped_with_reason_code`）。本決策須在 v3.5 plan §4.2 與 §5.4 兩處顯式記載此邊界。

**關鍵衝突 5（Artifact Obligation Matrix vs document generation）**：FIND-33 之 obligation matrix 容易被誤解為「自動生成 SRS / RTM / threat model 文件」；prompt -1 顯式禁止 document content generation，要求 matrix 為 `presence_only: true`，僅驗證 artifact 是否該存在，不生成內容。本決策須在 v3.5 plan §4.3 與 §5.5 兩處顯式記載此邊界。

## Options Considered

- **A. 拒絕執行，要求 user 先讓 v3.5.0 進 v3.4 之 manifest**：違反 v3.5.0 為「品質控制面」之獨立性；v3.4 chain 已封閉，不應再開動。
- **B. 將 v3.5.0 標為 v3.4 之 supersession**：違反 user prompt 之顯式 `builds_on` 要求；破壞 v3.4 evidence chain 之 audit trail。
- **C. 接受 v3.5.0 為獨立 plan_version，與 v3.4 並存（builds_on，not supersedes）**：v3.4 chain 之證據保留為 audit baseline；v3.5.0 為新 control surface，補強 v3.4 既存 governance；後續代理據此區分 v3.4 stable controls 與 v3.5 新 controls。

## Reasoning

1. **artifact-first 原則之精神延續**：v3.4 之 TASK-1020 已為「artifact-first 不可逆轉」立第一個顯式落地；v3.5.0 之 TASK-1023 沿用此設計（task → plan → decision → verify → status，後成 plan 文件本身），不再復發 v3.3 之 zombie 失敗模式。
2. **builds_on 而非 supersedes**：v3.4 chain 之證據（TASK-1005..1019、1012、1016 之 commit hashes、verify artifacts、manifest）為治理修復之 audit baseline；若 v3.5.0 supersede 之，後續代理將失去 v3.4 證據之合法基礎。`builds_on` 之語義保證 v3.4 控制（如 verify floor、threat model、red team execution）持續有效；v3.5.0 在其上增加 quality control surface 層。
3. **Option A 風險**：拒絕執行將使 v3.5.0 永久 stuck；user prompt 已顯式接受「v3.5.0 為新檔，不直接編輯 v3.4」，故不視為阻塞前提。
4. **Option B 風險**：宣告 supersedes 將破壞 v3.4 evidence chain；plan §Risks R1 已列此為 blocking risk；本 decision 必須在 plan / manifest / decision 三層顯式落實 `supersedes: null`。
5. **Option D 風險**：改寫 v3.4 plan 違反 chain seal 之 immutability；TASK-1016（end-to-end smoke test，commit `2403c98`）之 audit trail 將失效。

**v3.4 與 v3.5.0 之 control surface 區分**：

- v3.4 controls（持續有效）：verify floor baseline、threat model rebuild、red team execution / regression、RACI auditor v2、Assurance strict/legacy、context hygiene、baseline repair。
- v3.5.0 controls（在 v3.4 之上新增）：source/template exact-sync gate、JSON schema validation gate、import-time side-effect gate、golden CLI output harness、minimal PCACC（四條結構檢查）、artifact obligation matrix（presence-only）、waiver expiration enforcement。

兩 plan_version 並存時，後續代理應同時讀 v3.4 與 v3.5.0；若有衝突，以較新之 v3.5.0 為主，並產出新 decision artifact 記錄衝突解決。

- prompt -1 顯式要求「role definitions are global，model assignments are per-task」。此設計使 implementer / architecture_critic / negative_tester / final_approver 之 role 定義不被 model brand 綁死；同時，per-task metadata 可記錄此次 implementer 是 Claude Code、negative tester 是 Codex 等資訊，便於 audit。
- final_approver 必須為 human：避免 AI 自我簽核之循環；arcobaleno 為 v3.5.0 之 final_approver。

**雙標 Decision Class 之合理性**（沿用 TASK-1020 framing）：
