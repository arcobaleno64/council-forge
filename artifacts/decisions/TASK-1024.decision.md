## Issue

v3.5.0 plan introduction（TASK-1023，commit `a40f6bc`）已確立 quality control surface 之五條 findings（FIND-29 至 FIND-33）。其中 FIND-29（source/template sync fragility）與 FIND-30（validator and test monolith maintainability risk）需要在 enforcement 之前先做 baseline 量測，否則：

1. **無 baseline-aware enforcement**：TASK-1025 P0 quality gates 採 baseline-aware rollout（Phase 1 baseline freeze、Phase 2 strict on new/modified、Phase 3 full repo strict — Phase 3 不在 v3.5.0 scope）。Phase 1 / 2 必須仰賴一份 frozen baseline 區分「existing drift」與「new drift」。沒有 baseline，gate 將無法區分既有狀態與新違規。
2. **無 monolith refactor 證據**：FIND-30 提到 validator / test monolith 風險，但 v3.5.0 顯式禁止真拆檔；v3.5.1 / v3.6 之 split 候選需有 LOC / function_count / responsibility 量測作為 prerequisites。沒有 baseline，後續 split 決策將失去客觀依據。
3. **無 cross-model drift 量測**：FIND-31（multi-model style and behavior drift）需要 JSON schema surface、import-side-effect surface、CLI output surface 三層 inventory，作為 TASK-1025 之 QC-SCHEMA-001 / QC-IMPORT-001 / QC-GOLDEN-001 enforcement 對象。

**關鍵衝突 1（量測 vs 修復）**：team / 後續代理可能誤把 baseline inventory 之 drift 發現視為「該立即修」，導致：

- 對 `template/artifacts/scripts/test_guard_units.py` 執行 `cp` / `cat >` / `git checkout` 強制對齊 root，掩蓋 baseline 真實狀態。
- 對 `backfill_pdca_labels.py` 與 `classify_existing_tasks.py` 兩 root-only script 強制 copy 至 `template/`，未經 decision artifact 證成 sync contract 是否該擴展。
- 對 monolith 立即 split，違反 v3.5 plan §5.6 之 version split rule（v3.5.0 = controls before refactor）。

本 decision 顯式禁止此三類「順手修」之路徑。

**關鍵衝突 2（量測工具 vs 副作用）**：要量測 LOC / function_count / sha256，自然會想用 `python -c "..."`、`cloc`、`tokei`、`ruff stats` 等工具；但這些可能：

- 創建 `__pycache__`（Python 任一 import）。
- 創建 `.pytest_cache`（pytest 啟動）。
- 創建 cloc / tokei 之臨時報告檔。
- 觸發 ruff 之 cache。

任一副作用都違反 prompt §2 之 hard non-goals 與 §4 之 forbidden during preflight。本 decision 顯式選擇 `wc -l` + `grep -cE` + `sha256sum` + ripgrep 之最小工具集，避免任何 cache emission。

**關鍵衝突 3（baseline_id 穩定性）**：source/template pair 與 drift entry 之 `baseline_id`（如 QB-SYNC-0001、QB-DRIFT-0001）一旦發出，TASK-1025 / 1026 / 1027 / v3.5.1 / v3.5.2 / v3.6 都會引用。若 ID 在後續 baseline rerun 中重新分配，所有引用都將失效。本 decision 確立「baseline_id once assigned, never reassigned」之穩定性原則。

**關鍵衝突 4（FIND-18 status 之誘惑）**：baseline 量測完成後，team 可能誤判「source/template inventory 已完成 → FIND-18 可以宣告 Mitigated」。但 v3.5 plan §7 明文 FIND-18 transition 須四項齊備（exact-sync guard、drift regression case、decision path evidence、clean guard_contract_validator）；TASK-1024 只提供 baseline，**不**提供 enforcement、亦不提供 regression case。本 decision 顯式禁止 TASK-1024 升級 FIND-18 status。

## Options Considered

- **A. 跳過 baseline，直接由 TASK-1025 一邊實作 gate 一邊量測**：違反 baseline-aware enforcement 之設計；TASK-1025 將同時承擔量測 + 實作 + enforcement 三責，scope 失控；且無法在 enforcement 啟動前讓人類 reviewer 看到 baseline。
- **B. baseline 量測同時順手 normalize drift（讓所有 sync pair 變 in_sync）**：違反 v3.5 plan §0.3 scope lock 與 prompt §2 hard non-goals；掩蓋真實 baseline；破壞 TASK-1025 enforcement input；且若 normalize 引入未審核之 source/template 變動，將違反 [CLAUDE.md](../../CLAUDE.md) §3「Surgical Changes」與 RACI accountability。
- **C. baseline 量測，drift 列為 baseline state 不修，remediation 屬 TASK-1025 與其後**：保持 inventory-only；existing drift 透過 baseline_id 穩定追蹤；TASK-1025 透過 QC-SYNC-001 + waiver schema with expires_at 處理 remediation。
- **D. baseline 量測同時順手做 monolith split / policy registry extraction**：違反 v3.5 plan §5.6 version split rule（v3.5.0 = controls before refactor，v3.5.1+ 才允許 split）；違反 prompt §2 hard non-goals；split 與 baseline 量測為兩件不同性質之工作（量測 vs 結構演化），混做將使 commit 不可審核。
- **E. baseline 量測使用重型工具（cloc / tokei / ruff stats / python -m）**：可能引入 `__pycache__`、cache 報告檔；違反 §4 forbidden tools；且若工具版本差異（不同機器 cloc 回不同 LOC），baseline 將失去跨機器穩定性。

## Chosen Option

**C** — baseline 量測，drift 列為 baseline state 不修，remediation 屬 TASK-1025 與其後。

工具選擇：`wc -l` + `grep -cE` + `sha256sum` + ripgrep。不執行任一 `python` 指令、不 import 任一 repo module、不執行任一 cache-emitting tool。

## Reasoning

1. **artifact-first lifecycle 延續**：TASK-1023 之雙標 decision_class（governance-quality-control-surface-introduction）已立 v3.5.0 framing；本 decision 沿用相同 framing，使 forward-compat 與 backward 相容並存。
2. **baseline-aware enforcement 之合法基礎**：TASK-1025 之 P0 gates 採 Phase 1 baseline freeze / Phase 2 strict on new/modified；Phase 1 與 Phase 2 共同 prerequisite 為「一份 frozen baseline」。本任務即此 baseline 之來源；不做即無下一步。
3. **drift 不修之合理性**：existing drift 為 baseline 真實狀態，是 TASK-1025 enforcement input 而非 violation。若 TASK-1024 順手修，TASK-1025 將失去「區分 existing 與 new」之能力，rollout 模型失效。本 decision §Issue §關鍵衝突 1 已詳列三類禁止之「順手修」路徑。
4. **工具最小化之必要性**：v3.5 plan §3.2 列禁工具（pytest / ruff / mypy / pyright / formatters / validators that emit reports）；prompt §2 進一步禁 `__pycache__` 等 cache。`wc` / `grep` / `sha256sum` / ripgrep 為唯一不引入 side effect 之計量工具集。
5. **monolith split 之 deferral**：FIND-30 量測（test_guard_units.py 12801 LOC / 1341 functions、guard_status_validator.py 2678 LOC / 105 functions）顯示 split 必要性；但 v3.5 plan §5.6 明文 v3.5.0 = controls before refactor，split 屬 v3.5.1 / v3.6。本 decision 將 split 候選紀錄於 baseline JSON `metrics`（responsibility_tags）作為 v3.5.1 / v3.6 input，**不** 在 v3.5.0 啟動 split。
6. **FIND-18 不升級之必要性**：v3.5 plan §7 明文 FIND-18 transition 四 prerequisites；本任務只提供 baseline 量測（一項 prerequisites 之前置條件），未提供 exact-sync guard 實作、drift regression case、clean validator run。即便 baseline 完成，FIND-18 仍須留 `In-Progress`。本 decision 顯式禁止 TASK-1024 升級 FIND-18。
7. **post-commit verification 之分工**：Claude Code 為 implementer，自行驗證後 commit；Codex 為 negative_tester，post-commit 做 PASS/FAIL 獨立驗證；arcobaleno 為 final_approver。此分工符合 v3.5 plan §5.3 agent_roles policy（同 model 不可同時為 implementer 與 final_approver；final_approver 必須為 human）。
