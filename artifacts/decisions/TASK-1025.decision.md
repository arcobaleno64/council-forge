**關鍵衝突 1（gate vs remediation）**：team / 後續代理可能誤把 「P0 gate 上線」 視為 「應一併把 baseline drift 修掉」。但：

## Chosen Option

**C** — 實作 baseline-aware gate runner，drift 視為 baseline_existing pass。

實作細節：

- runner = stdlib-only Python 3 script（shebang `#!/usr/bin/env python3`）。
- gate 函式各自獨立，便於後續 v3.5.x 擴展。
- subprocess + `PYTHONDONTWRITEBYTECODE=1` + `-B` flag 三層防護避免 `__pycache__`。
- waiver discovery 採 explicit policy waivers array；v3.5.0 起始陣列為空。
- QC-IMPORT-001 first cycle 對 unlisted candidate 採 advisory；首批 expected_import_clean 僅含 `validate_context_stack.py`。
- runner 同步建立 source 與 template mirror，sha256 byte-identical。
- self-check 模式（`--self-check`）print to stdout，不寫 evidence file；evidence file 透過 `--output` 顯式產出。

## Reasoning

1. **artifact-first lifecycle 延續**：TASK-1023 / 1024 雙標 decision_class framing 已立 v3.5.0 governance pattern；本 decision 沿用 forward-compat + backward 相容設計。
2. **baseline-aware enforcement 是 v3.5.0 之核心 design**：baseline 凍結 + 新/變動 drift blocking 是 v3.5.0 區別於 v3.4「全 strict 直上」之關鍵；本 runner 是 design 之實作落地。
3. **stdlib-only 之必要性**：避免 third-party 依賴使 enforcement 在 minimal Python 環境（CI、freshly cloned dev）皆可運行；亦避免 supply-chain 風險。
4. **QC-IMPORT-001 三層防護之必要性**：Windows + Python 3.14 之 import 行為對 PYTHONDONTWRITEBYTECODE 通常合規，但 `-B` flag 是 command-level 強制，PYTHONNOUSERSITE 排除 user site 干擾，三層防護使結果可重現於不同環境。
5. **first cycle advisory 之合理性**：「實測 import-clean」不等於「永久承諾 import-clean」，未來 commit 可能引入 module-level side effect。將 expected_import_clean 列表作 enforcement 黃金清單，使 strict 升級透過顯式 task lifecycle 完成（每加一條須 review），是 baseline-aware 設計精神之延伸。
6. **runner template mirror 之必要性**：source/template sync contract 是 FIND-29 之核心；TASK-1025 自身若違反此 contract（root-only runner），等於 self-undermine。`cp -p` + sha256 byte-identical 是最小工具集，無 normalization、無編碼轉換。
7. **waiver discovery 保守邊界**：v3.5.0 first cycle 採 explicit policy waivers array，是「最小可驗證」設計；decision-artifact-driven discovery 若引入，將擴大 attack surface（例如「decision artifact 含 waiver block 可悄悄 bypass enforcement」），需更多設計審視，留給後續 task lifecycle。
