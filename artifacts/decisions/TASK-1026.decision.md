## Issue

TASK-1025 已 bootstrap baseline-aware P0 quality gates（commit `6da55ed`），但 P0 gates 之四條檢查（QC-SYNC-001 / QC-SCHEMA-001 / QC-IMPORT-001 / QC-GOLDEN-001）只覆蓋 `artifacts/scripts/` 與 schema artifact 的 surface，無法偵測 lifecycle artifact 之間的結構一致性。FIND-32（cross-artifact consistency blind spot）需獨立 control surface 接手。

v3.5 plan §4.2 規範 PCACC v3.5.0 為**結構性檢查**，恰四條 strict checks，明確排除 reasoning-faithfulness audit / belief-state audit / model self-confidence audit / free-text rationale / markdown SAVeR report 五類非結構性檢查。schema §5.4 規定 `output_policy.format = "json"`、`output_policy.free_text_rationale = false`、checks 恰四條。

**關鍵衝突 1（PCACC 與 reasoning audit 之邊界）**：team / 後續代理可能誤把 PCACC 視為「LLM agent 自我審計工具」，順手加入 belief-state / confidence_score / reasoning_trace 等欄位。但：

- v3.5 plan §4.2 明確禁止此類擴張；任何擴張須以新 task lifecycle 與 decision artifact 顯式授權。
- 結構檢查與 reasoning 檢查之 evidence 性質不同：結構檢查可由 file existence / parse / canonical match 收結，reasoning 檢查需 ground truth 評分標準（v3.5.0 沒有此 ground truth）。
- 混合二者將使 PCACC output schema 不穩定，後續 v3.5.1 / v3.6 演化困難。

對策：policy `output_policy.forbidden_check_fields` 明列六個禁用欄位（rationale、free_text_rationale、belief_state、reasoning_trace、confidence_score、self_audit）；runner 之 build_result() 不寫此六欄；validate_policy() 在 runner 啟動時雙鎖（`free_text_rationale must be False`、`format must be json`、`checks length must be 4`）。

**關鍵衝突 2（PCACC-002 evidence ref 之 false positive）**：verify artifact 之 `## Evidence Refs` 區段允許多種 ref 形式（repo-relative path、HEAD / commit hash、外部 URL 等）。若 PCACC-002 採過嚴規則：

- 將 commit hash 誤判為 missing path → false fail。
- 將 markdown link `[label](path)` 之 label 部分誤判為 path → false fail。
- 將 「HEAD at task start: 6da55ed」之說明文字誤判為 path → false fail。

對策：runner 之 `parse_evidence_refs()` 顯式分類三類 ref：

1. repo-relative artifact / docs / template / governance prefix → file existence check。
2. HEAD / commit hash / 含 `=` 之 marker → 視為 resolved metadata（不需 file existence）。
3. URL / 絕對路徑 / Windows drive 路徑 → malformed（fail）。

verify artifact 之 Evidence Refs 採純 repo-relative path 形式為主，commit metadata 用獨立行 + 顯式 prefix。

**關鍵衝突 3（PCACC-003 canonical reviewer registry）**：v3.5 plan §5.3 明文 `final_approver MUST be human`、`forbidden: global model-brand-to-role binding`。但 PCACC-003 需 canonical reviewer set 才能判 pass / fail。

對策：採「policy-embedded canonical set」設計：

- canonical_reviewers 與 canonical_owners 嵌於 policy.checks[PCACC-003] 之欄位中。
- 首批保守：canonical_reviewers=`["arcobaleno"]`，canonical_owners=`["Claude", "Codex", "Gemini"]`。
- canonical 為**人類 reviewer ID**或**agent class name**（與 agent_label `claude-code` / `codex` / `gemini` 區隔，避免 brand-to-role 全域綁定）。
- 後續 task lifecycle 若需擴張，須以新 decision artifact 顯式擴展 policy 之 canonical set；不從 task.md 自動推導。

policy 缺少 canonical 欄位時，runner 回 `skipped_with_reason_code` + `canonical_registry_missing_in_policy`，不 silent pass。

**關鍵衝突 4（PCACC-004 timestamp 嚴格性）**：v3.5 plan §4.2 規定 PCACC-004 為「Decision review_timestamp is later than evidence_generated_at」。但何處讀 review_timestamp、何處讀 evidence_generated_at，prompt 留有彈性。

對策：採以下優先順序：

- review_timestamp：先 `status.last_updated`、再 `verify.Last Updated`（兩者皆可作為 review 之代理 timestamp）。
- evidence_generated_at：先 `status.self_check_result_ref` 對應檔之 `generated_at`、再 `artifacts/verify/<task>/precommit-check-result.json` 之 `generated_at`、再 `artifacts/verify/<task>/*.json` 任一含 `generated_at` 之檔。
- strict 比較：`review_ts > evidence_ts` 為 pass；equal 為 fail（代理「review 未真正在 evidence 之後」）；review < evidence 為 fail。
- 任一 missing → `skipped_with_reason_code` + 顯式 reason_code（`no_review_timestamp` / `no_evidence_generated_at` / `no_review_or_evidence_timestamp`）。

對 docs-only 任務（如 TASK-1023）無 evidence file，PCACC-004 將回 `skipped_with_reason_code`；這是設計意圖，不視為 fail。

**關鍵衝突 5（PCACC runner 與 TASK-1025 quality gate runner 之邊界）**：team 可能順手把 PCACC 加入 `run_quality_gates.py`。但：

- PCACC 為 cross-artifact 結構檢查，與 P0 quality gate（source/template、JSON schema、import side-effect、CLI golden）為不同 surface。
- 混合二者會違反 single responsibility 原則，使 v3.5.1 / v3.6 演化困難（如 PCACC AC coverage 加入時，run_quality_gates.py 將被迫一併修改）。

對策：PCACC 採獨立 runner `run_precommit_check.py`，獨立 policy `precommit-check-policy.v3.5.json`；TASK-1025 deliverable（`run_quality_gates.py` / `quality-gate-policy.v3.5.json` / `quality-baseline.v3.5.json`）**完全不被** TASK-1026 修改。verify artifact 之 AC-16 以 `git diff <TASK-1025 commit>..HEAD -- ...` 證實。

## Options Considered

- **A. 不實作 PCACC runner，僅產出 policy 文件**：違反 prompt §1 required final behavior 第 3 / 4 項；policy 沒有 enforcement 機制等於沒有；後續 phase 無實作可繼承。
- **B. 實作 PCACC runner 並把 reasoning faithfulness / belief-state / SAVeR 等納入**：違反 prompt §2 hard non-goals 與 v3.5 plan §4.2 之顯式排除清單；混合結構檢查與推理檢查使 schema 不穩定；free-text rationale 違反 prompt §10 / §17 之 no rationale 規約。
- **C. 實作 PCACC runner 含恰四條 strict structural checks，排除清單顯式列入 policy.excluded_checks，runner 拒絕 free-text 欄位輸出**：保 v3.5.0 minimal scope；PCACC 為獨立 surface；後續擴張（如 v3.5.1 AC coverage）以新 task lifecycle 顯式授權。
- **D. 把 PCACC 邏輯加入 TASK-1025 之 `run_quality_gates.py`**：違反 single responsibility；混合 P0 quality gate 與 PCACC 兩 surface；違反 prompt §2 「do not modify TASK-1025 quality gate runner unless absolutely required」（PCACC 是獨立 surface，無此 absolute requirement）。
- **E. 跳過 PCACC-003 canonical reviewer 檢查，採 silent pass**：違反 prompt §13 「missing registry must not silently pass」；放棄 final_approver canonical 控制；引入 governance hole（任意 reviewer 都可批 final）。

## Chosen Option

**C** — 實作 PCACC runner 含恰四條 strict structural checks。

實作細節：

- runner = stdlib-only Python 3 script（shebang `#!/usr/bin/env python3`）。
- 四 PCACC 函式各自獨立，便於後續 v3.5.x 擴展（不擴張至 reasoning audit）。
- canonical reviewer / owner set 嵌於 policy；缺失 → `skipped_with_reason_code`，不 silent pass。
- timestamp 比對嚴格（`review > evidence`）；missing → `skipped_with_reason_code`。
- runner 同步建立 source 與 template mirror，sha256 byte-identical。
- self-check 模式（`--self-check`）print to stdout，不寫 evidence file；evidence file 透過 `--output` 顯式產出。
- exit codes: 0=pass、1=blocking failure、2=invocation error。

## Reasoning

1. **artifact-first lifecycle 延續**：TASK-1023 / 1024 / 1025 雙標 decision_class framing 已立 v3.5.0 governance pattern；本 decision 沿用 forward-compat + backward 相容設計。
2. **PCACC 為結構檢查之必要性**：FIND-32 cross-artifact consistency blind spot 需獨立 control surface；P0 quality gate（TASK-1025）覆蓋 source/template + schema + import-time + CLI 四 surface，但對 lifecycle artifact 之間的結構一致性無覆蓋。PCACC 補上此缺口。
3. **stdlib-only 之必要性**：避免 third-party 依賴使 enforcement 在 minimal Python 環境（CI、freshly cloned dev）皆可運行；亦避免 supply-chain 風險。
4. **不 import repo modules 之必要性**：PCACC runner 透過 file system 操作（read text、parse JSON / metadata block）即可完成所有四檢查；不需 import 任何 repo module，避免 `__pycache__` 副作用。
5. **恰四條 checks 之必要性**：v3.5 plan §4.2 / §5.4 規定恰四條，不多不少。runner 之 `validate_policy()` 在啟動時驗 checks length=4；任何 future extension 須以新 task lifecycle 顯式擴展 policy + runner，不從 v3.5.0 静默擴張。
6. **PCACC-002 evidence ref 寬鬆策略之合理性**：verify artifact 之 Evidence Refs 已是現行慣例（含 commit hash、HEAD marker、artifact path 並列）；嚴格規則將迫使所有歷史 verify artifact 重寫，違反 v3.5.0 minimal-scope 精神。寬鬆策略保留 false-fail 風險於 R1，由 verify artifact 寫法收結。
7. **PCACC-003 canonical set 嵌於 policy 之合理性**：避免「全域 reviewer 配置檔」之 governance bloat；canonical set 跟著 policy 走，policy 由本 decision 授權；擴張 canonical set 須以新 decision 顯式擴展。
8. **PCACC-004 strict comparison 之合理性**：equal timestamp 表示「review 未真正在 evidence 之後」（如手動回填同一 timestamp），這是 review 流程之異常信號，應 fail；若 review 與 evidence 為 batch 同時生成，須補 ≥1 秒間隔，這是 review process 之自然要求。
