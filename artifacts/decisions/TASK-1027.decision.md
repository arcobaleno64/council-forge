## Issue

v3.5.0 finding FIND-33（artifact obligation ambiguity）需 control surface 接手：v3.4 對「該 task 該不該有 X artifact」採隱性慣例；缺少明確 obligation matrix；artifact bloat 風險高（過度生成 SRS / RTM / design spec / threat model / runbook 等長文件）；對應地，small task 之 under-documentation 與 high-risk task 之 missing governance artifact 兩端問題並存。

v3.5 plan §4.3 規範 TASK-1027 為 **presence-only matrix**，恰列 `matrix_version` / `effective_from` / supersession policy / legacy task policy；明確排除 SRS / RTM / design spec / threat model / release note / migration note / user guide / runbook 之內容生成。schema §5.5 規定 `presence_only=true`、`effective_from` 必填、supersession_policy 必含四欄。

**關鍵衝突 1（matrix 與 document generation 之邊界）**：team / 後續代理可能誤把 matrix 視為「artifact 內容自動生成器」，順手把 SRS / RTM / threat model / release note 之段落內容寫入 matrix JSON 之 catalog description 或 rule notes 欄位，甚至建獨立 .md 檔。但：

- v3.5 plan §4.3 / prompt §15 明確禁止此類擴張；matrix MAY 要求 PRESENCE，**不**生成 CONTENT。
- presence control 與 content generation plane 之 evidence 性質不同：presence 可由 file existence / glob 收結，content generation 需 ground truth 與評審流程（v3.5.0 沒有此機制）。
- 混合二者將使 matrix 退化為「治理機構自動產文工具」，與 anti-bloat 初衷相反。

對策：matrix JSON 之 `forbidden_generation` 區段顯式列八項 forbidden_content_classes（srs / rtm / design_spec / threat_model / release_note / migration_note / user_guide / operation_runbook），scope 字串明示「matrix MAY define when these artifacts are required or optional for OTHER tasks; it MUST NOT author them」；本任務 commit staged set 嚴限六檔（5 lifecycle + matrix policy），任一新增 .md 內容檔被 staged 立即 `git restore --staged`。

**關鍵衝突 2（completed task 是否 retroactive 重評）**：matrix 變更時，team 可能誤對 TASK-1023 / TASK-1024 / TASK-1025 / TASK-1026 等已完成任務 retroactive 套用新 matrix；或對 v3.4 chain 之歷史任務 retroactive 套用。但：

- 已完成任務之治理證據已封閉（TASK-1016 chain seal）；retroactive 套用會無條件「重新發明歷史 obligation」，違反 artifact-first lifecycle 之 audit immutability。
- legacy task 完成於 effective_from 之前，無從預期未來 matrix 規則；若強制 retroactive，將使所有歷史任務無條件「非合規」，引發治理癱瘓。

對策：matrix.supersession_policy.completed_tasks_retroactive_evaluation = `false`；matrix.legacy_task_policy.pre_matrix_tasks_retroactive_evaluation = `false`、pre_matrix_tasks_advisory_only = `true`；matrix_changes_apply_from_effective_from_forward = `true`。任何 matrix 演化（v3.5.1 / v3.6）須宣告新 effective_from 與新 matrix_version，僅對該日後新建 / 修改 / superseding 之任務生效。

**關鍵衝突 3（superseded task 之 obligation 流向）**：當任務 A 被任務 B supersede，A 之未結 obligation 是否自動轉嫁 B？三種選擇：

- (a) 完全不轉嫁：B 從零開始，A 之未結 obligation 永久懸空。
- (b) 完全轉嫁：B 必繼承 A 之全部 open obligation。
- (c) 預設轉嫁但允許 decision artifact 顯式 waive：B 繼承 A 之 still-open obligation，除非 B 之 decision artifact 明示 waive 該 obligation。

對策：採 (c) — superseded_task_obligation_state = `frozen`（A 之原 obligation 凍結於 supersession 時點）；superseding_task_inherits_open_obligations = `true`（B 預設繼承）；waiver_requires_decision_artifact = `true`（B 須以 decision artifact 顯式 waive 才能解除繼承）。

**關鍵衝突 4（waiver mechanism 是否需 standalone registry）**：團隊歷次治理修復過程中，「waiver registry」議題反覆出現。三種選擇：

- (a) v3.5.0 立即建 standalone waiver registry：易引入 governance bloat；registry 自身須 schema、scoping、retention 規則；尚無數據顯示需要。
- (b) v3.5.0 完全不允許 waiver：與 v3.5 plan §5.2 之 waiver schema 衝突；高風險治理任務無逃生口。
- (c) v3.5.0 沿用 decision artifact `## Guard Exception` 機制：waiver 必為 structured field（非 narrative paragraph）、必含六欄、必有 `expires_at`；過期 waiver 無效；不建 standalone registry。

對策：採 (c) — matrix.waiver_policy.mechanism = `decision_artifact_only`；no_standalone_registry_in_v3_5_0 = `true`、no_style_debt_registry_in_v3_5_0 = `true`；narrative_only_waiver_invalid = `true`；required_waiver_fields 列六欄（rule_id / scope / reason_code / owner / evidence_ref / expires_at）；expired_waivers_are_invalid = `true`。資料若未來顯示需要 standalone registry，由 v3.5.2 lifecycle 顯式授權。

**關鍵衝突 5（assurance_level 是否擴張加入 `high`）**：prompt §9 之 `risk_level` 列舉含 `low / medium / high / critical`；team 可能誤把 `high` 類比至 `assurance_level`。但：

- docs/artifact_schema.md §5.11.1 已明文「`high` is NOT a valid assurance level and must be rejected by validators」；TASK-1008 已強化此規約。
- assurance_level 與 risk_level 為兩個正交軸（assurance 為驗證強度、risk 為 blast radius）；混淆兩者將使 strict mode validator 拒絕 matrix。

對策：matrix.rule_axes.assurance_level.allowed_values = `["poc", "mvp", "production"]`、forbidden_values = `["high"]`；rule_axes.assurance_level.description 引用 docs/artifact_schema.md §5.11.1；所有 11 條 rule 之 assurance_level 嚴限 {poc, mvp, production}。

**關鍵衝突 6（generated_document_candidate 是否可作為 conditional required）**：對 high_risk_governance_change 與 security_sensitive_change 與 production_customer_facing_change 三類任務，threat_model / release_note / user_guide / migration_note 是否該設為 required-by-default？兩種選擇：

- (a) 設為 required-by-default：避免 under-documentation；但會使每個高風險任務無條件背 4-8 個長文件之 presence 義務，造成 artifact bloat。
- (b) 設為 optional-with-conditional-escalation：只有當 task 實際觸發特定 trigger（security 行為改變、user-visible 行為改變、需 user-side migration）時才升為 required；escalation 須記錄於該任務之 decision artifact。

對策：採 (b) — AOM-009（high_risk_governance_change）之 threat_model / release_note / migration_note 不在 required，僅在「視 trigger 條件」由 task decision artifact 顯式 escalate；AOM-010（security_sensitive_change）之 threat_model 為 optional；AOM-011（production_customer_facing_change）之 release_note / user_guide / migration_note 為 optional。matrix.rule_application_notes.conditional_escalation 明文「Escalation MUST NOT be inferred silently」。

## Options Considered

- **A. 不交付 matrix policy，僅產出 lifecycle artifacts**：違反 prompt §1 required final behavior 第 2 / 3 / 4 項；無 policy 等於無 control；後續 phase 無基準可繼承。
- **B. 交付 matrix 並含 SRS / RTM / threat model 等內容章節（混合 presence 與 content）**：違反 prompt §2 hard non-goals 與 §15 forbidden_generation；混合 presence control 與 content generation 使 matrix 退化為「治理機構自動產文工具」；違反 anti-bloat 初衷。
- **C. 交付 presence-only matrix；含 11 條 rules（5 anchor + 6 generic）；含 supersession / legacy / waiver policy；不含內容生成；不含 runtime validator**：保 v3.5.0 minimal scope；matrix 為獨立 surface；後續擴張（如 v3.5.1 validator 或 v3.5.2 waiver registry）以新 task lifecycle 顯式授權。
- **D. 交付 matrix 並順手實作 runtime validator**：違反 prompt §2 「do not implement a semantic validator」與 「do not implement a broad artifact validator」；混合 policy 與 enforcement 兩 surface；違反 single responsibility；若 validator 邏輯有錯，policy 與 validator 須同時改，演化困難。
- **E. 交付 matrix 但 retroactive 套用至 TASK-1023..TASK-1026**：違反 prompt §13 / §17 「completed tasks are not retroactively re-evaluated」；引入 audit immutability 漏洞；TASK-1023..TASK-1026 已封 verify pass，retroactive 套用無條件破壞 chain seal。
- **F. 交付 matrix 但建 standalone waiver registry**：違反 prompt §2 「do not perform validator module split」+ 「do not extract policy registry」之精神（雖文字未直接禁 waiver registry，但 v3.5 plan §5.2 / TASK-1025 decision §Implications 已立 v3.5.0 不建 waiver registry 之原則；prompt §14 亦明示「No standalone waiver registry in TASK-1027」）；引入 governance bloat；尚無數據支持。

## Chosen Option

**C** — 交付 presence-only matrix policy（11 條 rules + supersession / legacy / waiver policy + forbidden_generation + limitations），不含內容生成，不含 runtime validator。

實作細節：

- matrix = JSON only（schema_version=`artifact-obligation-matrix/v1`、presence_only=true）。
- 三軸（task_type / risk_level / assurance_level），assurance_level 嚴限 {poc, mvp, production}。
- artifact_catalog 五類分組，generated_document_candidate 列八項候選但不生成內容。
- 11 條 rule（AOM-001..AOM-005 anchor + AOM-006..AOM-011 generic）；每條八欄齊備。
- supersession_policy 五欄、legacy_task_policy 四欄、waiver_policy 六欄齊備。
- forbidden_generation 顯式列八項 + scope 字串明示。
- limitations 十條保守說明。
- runtime validator 不實作；matrix enforcement 屬 future task lifecycle。
- 本任務 commit staged set 嚴限 6 檔（5 lifecycle + 1 policy）。

## Reasoning

1. **artifact-first lifecycle 延續**：TASK-1023 / 1024 / 1025 / 1026 雙標 decision_class framing 已立 v3.5.0 governance pattern；本 decision 沿用 forward-compat + backward 相容設計（YAML frontmatter 用新 taxonomy `governance-artifact-obligation-matrix`、markdown body 用既有 `conflict-resolution`）。
2. **matrix 為 presence control 之必要性**：FIND-33 artifact obligation ambiguity 需獨立 control surface；既有 PCACC（TASK-1026）覆蓋 lifecycle 結構檢查、quality gates（TASK-1025）覆蓋 source/template/schema/import/CLI 五 surface，皆**不**覆蓋「該 task 該不該有 X artifact 類型」之 obligation control。matrix 補上此缺口。
3. **presence-only 之必要性**：content generation 屬不同 governance plane，需 ground truth、評審流程、版本化規約；v3.5.0 沒有此機制；混入 content generation 會使 matrix 退化為「治理機構自動產文工具」，與 anti-bloat 初衷相反。
4. **不實作 runtime validator 之必要性**：matrix policy 與 validator 為兩個 surface（policy 為宣告 / validator 為執行）；v3.5.0 之精力應花在 policy 正確性（rule design + supersession semantics + waiver mechanism），而非 validator 實作；validator 屬 future task lifecycle 之獨立交付。
5. **assurance_level 嚴限 {poc, mvp, production} 之必要性**：與 docs/artifact_schema.md §5.11.1 一致；strict mode 已拒絕 `high`；matrix 若引入 `high` 將被自身規約拒絕，邏輯破裂。
6. **conditional escalation 之合理性**：generated_document_candidate（threat_model / release_note / migration_note / user_guide）若預設 required，會使每個高風險任務背 4-8 個長文件 presence 義務，造成 artifact bloat 反向問題；採「optional-with-conditional-escalation」設計，由 task decision artifact 顯式記錄 trigger，符合 anti-bloat 與 evidence-based 雙原則。
7. **supersession (c) 設計之合理性**：完全不轉嫁會留 governance hole（A 之 obligation 永久懸空）；完全轉嫁太僵硬；「預設轉嫁 + decision artifact 顯式 waive」兼顧默認一致性與必要彈性。
8. **legacy task advisory-only 之合理性**：對 effective_from 之前任務 retroactive 套用會無條件破壞 audit immutability；advisory-only 保留追溯資訊但不強制合規；只有 modified / superseding 兩條件觸發 current matrix 套用。
9. **waiver_policy decision_artifact_only 之合理性**：避免 standalone registry bloat；waiver 跟著 task decision 走，scope / owner / reason / evidence / expires 顯式；narrative-only 不算（避免 audit-resistant 自由文字）；過期 waiver 無效（避免永久豁免）。

### 對 TASK-1023..TASK-1026 之回顧驗證（advisory-only，非 retroactive enforcement）

雖然 matrix `legacy_task_policy.pre_matrix_tasks_retroactive_evaluation = false`，仍可作為自洽性 sanity check：將 11 條 rule 對 TASK-1023..TASK-1026 之 obligation 與實際交付 cross-check，預期所有四任務皆滿足 anchor rule（AOM-001..AOM-004）之 required_artifacts，且未觸及任一 forbidden_artifact。實際結果於 verify artifact §Self-Consistency Check 揭露。此 cross-check 為 advisory，**不**對 TASK-1023..TASK-1026 之 status 做任何修改。
