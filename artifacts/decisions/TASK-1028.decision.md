## Issue

v3.5.0 治理品質控制面（TASK-1023..1027）已封閉，但 control surface 之證據結構僅含「正向 self-check」（runner 對自身 commit 跑 self-check pass）。負向證據（受控 negative test 證明 control 真能擋下被預測之 violation）尚缺；validator monolith 之 characterization coverage 仍稀薄；FIND-30 若於缺乏 negative test 與 characterization 之下進入 module split，refactor 風險高。

v3.5 manifest `version_split_rule.v3.5.1` 字面為「refactor only after controls are green: allow small validator split candidates; forbid new governance plane」。此字面有兩個歧異：

- (a) **「allow small validator split candidates」之解讀**：可解讀為「允許 split 本身」或「允許 split _readiness_ work（characterization、negative test、design decision）」。
- (b) **「controls are green」之判定**：v3.5.0 self-check 為 pass，但缺乏 negative test 證明 control 真能擋；若僅以「self-check pass」判定 controls green，將過早允許 split。

**關鍵衝突 1（split 是否在 v3.5.1 啟動）**：

- 若採 (a) 之第一解讀（允許 split 本身），v3.5.1 可立即啟動 small validator split candidates；但 v3.6 之啟動條件為「v3.5.x characterization tests 與 gates 維持綠至少一個 release cycle」，若 v3.5.1 即 split，將跳過 characterization 階段，違反 v3.6 condition。
- 若採 (a) 之第二解讀（允許 split _readiness_ work），v3.5.1 之 task 為 negative test + characterization + design decision，split 本身延至 v3.6；此解讀與 v3.6 啟動條件對齊。

對策：採 (a) 之第二解讀。本 decision 顯式記載：v3.5.1 將「allow small validator split candidates」**緊縮**為「allow split _readiness_ work；split 本身延至 v3.6」。理由：

- v3.5.0 缺乏 negative test 證明 controls 真能擋（即 controls green 之判定弱）。
- v3.5.0 缺乏 characterization coverage（FIND-30 之 monolith maintainability risk 之原因即在缺乏 characterization）。
- v3.6 啟動條件（characterization tests 與 gates 維持綠至少一個 release cycle）若 v3.5.1 即 split，根本無法滿足。
- 緊縮為 in-spirit refinement：v3.5.1 仍是「refactor readiness 階段」，只是把 readiness 之語義具體化為「先 prove + characterize + decide policy registry，再 split」。

**關鍵衝突 2（controls green 之判定方式）**：

- 若採「self-check pass」即 green：過早；正向證據不等於 control 真能擋。
- 若採「negative test pass」即 green：v3.5.0 沒有 negative test；需 v3.5.1 之 TASK-1029 / TASK-1030 補齊。

對策：本 decision 顯式記載：v3.5.1 之「controls green」採嚴格定義 — **正向 self-check pass + 負向 controlled negative test pass + characterization green**三者齊備方可進 v3.6 split。v3.5.1 之 TASK-1029 / TASK-1030 補負向；TASK-1031 補 characterization。

**關鍵衝突 3（policy registry extraction 是否先於 module split）**：

- 若先 split 後 extract：split 完成後仍要把常數搬出，影響每個 split 結果；二次重構成本高。
- 若先 extract 後 split：先決定 policy data 與 execution logic 之邊界，split 時可清楚保留 logic 給 module、把 data 留給 registry；split 之 module 邊界更明確。
- 若不 extract 直接 split：policy data 散落於每個 split 之 module，一致性差；後續若要 extract，將觸發第三輪重構。

對策：本 decision 顯式記載：v3.5.1 之 TASK-1032 為 **policy registry extraction design decision**（不抽，只決策）。決策結果為 v3.6 split 之 input；v3.6 implementation 須引用 TASK-1032 decision 為依據。即「先決策再實作；先抽 policy registry 再做 module split」之規範由 v3.5.1 之 design decision 階段確立，但實際抽取與 split 皆延至 v3.6。

**關鍵衝突 4（v3.5.1 是否擴張 PCACC / P0 gates / AOM）**：

- 若擴張：v3.5.1 既然要 prove，何不順便加新 check？
- 若不擴張：v3.5.1 之 prove 僅針對 v3.5.0 已有之 control，避免 scope creep。

對策：本 decision 顯式記載：v3.5.1 **不**擴張 PCACC（嚴限 v3.5.0 之四檢查）、**不**擴張 P0 quality gates（嚴限 v3.5.0 之四 gate）、**不**擴張 AOM matrix（嚴限 v3.5.0 之 11 條 rule）。任何擴張須 separate decision artifact 與 v3.5.2 或更後 follow-up task 顯式授權。理由：v3.5.1 之主題為「prove + characterize + decide」，非「add more checks」；v3.5.0 既有 control 之 prove 與 characterization 已足以填滿 v3.5.1。

## Reasoning

1. **artifact-first lifecycle 延續**：TASK-1023..1027 雙標 decision_class framing 已立 v3.5.0 governance pattern；本 decision 沿用 forward-compat + backward 相容設計（YAML frontmatter 用新 taxonomy `governance-v3.5.1-scope-freeze`、markdown body 用既有 `conflict-resolution`）。
2. **v3.5.1 主題之必要性**：v3.5.0 已封閉但缺負向證據與 characterization；v3.5.1 補此 gap 是 v3.6 split 之先決條件；無 v3.5.1 之 prove + characterize + decide，v3.6 split 不應啟動。
3. **planning-only 之必要性**：planning 與 implementation 為兩個 surface；TASK-1028 之精力應花在 scope correctness（candidate task 邊界 + readiness criteria + decision criteria）+ chain consistency（DAG + non-authorization），而非 implementation；implementation 屬 TASK-1029..1032 與 v3.6 之 separate task lifecycle。
4. **緊縮 v3.5 manifest version_split_rule.v3.5.1 字面之必要性**：「allow small validator split candidates」字面允許 split，但 v3.6 啟動條件（characterization green for at least one release cycle）若 v3.5.1 即 split 則無法滿足；緊縮為「split _readiness_ work」是 in-spirit refinement，避免規約衝突。
5. **嚴格 controls green 判定之必要性**：自證為 pass 不等於真能擋；負向證據（控制能擋）+ 正向證據（自身 pass）+ characterization（行為已被特徵化）三者齊備方可宣告 controls green。
6. **先 design decision 後 implementation 之必要性**：policy registry 抽法直接影響 v3.6 split 結果；先決策再實作可避免「split 完才發現要 extract」之二次重構成本。
7. **不擴張 v3.5.0 控制面之必要性**：v3.5.1 主題為 prove + characterize + decide，非 add more checks；任何擴張屬 v3.5.2 或 v3.6 之 scope；v3.5.1 期間擴張會稀釋 prove 之 focus。
8. **fixture isolation 之必要性**：negative test 涉及違規 artifact / 違規 source/template pair / 違規 PCACC artifact；若寫入 production tree，將污染 v3.5.0 已封閉之 control surface；隔離 fixture 是 single responsibility 之保障。
9. **TASK-1028 staged set 嚴限 7 檔之必要性**：本任務為 planning-only；任何超出 7 檔之 staged 表示已越界（如新建 fixture、新建 runtime code、修改 v3.5.0 deliverable）；嚴格邊界是 scope discipline 之保障。

### 對 v3.5 manifest version_split_rule.v3.5.1 之緊縮論述（in-spirit refinement，非衝突）

v3.5 manifest 字面：「v3.5.1 — refactor only after controls are green: allow small validator split candidates; forbid new governance plane」。

本 decision 緊縮為：「v3.5.1 — gate proving and refactor readiness: prove v3.5.0 controls via controlled negative tests; characterize validator/test monolith; decide policy registry extraction; FORBID validator module split; FORBID policy registry implementation; FORBID document content generation; FORBID PCACC scope creep beyond four checks」。

對讀：

- **共同點**：兩者皆「forbid new governance plane」；兩者皆要求「controls are green」方可 refactor。
- **緊縮點**：本 decision 將「allow small validator split candidates」改為「allow split _readiness_ work（characterization、negative test、design decision）」，理由為 controls green 之嚴格定義（正向 + 負向 + characterization 三者齊備）尚未滿足；split 本身延至 v3.6。

此緊縮為**規約 refinement，非衝突**；本 decision 顯式記載以避免未來代理誤讀 v3.5 manifest 字面而提前啟動 split。
