**關鍵衝突 3（PCACC-NEG-006 之 expected_status 與 prompt 字面差異）**：

prompt §8.6「Missing timestamp with no reason code」明示「Expected behavior: PCACC-004 status = fail; reason_code indicates missing timestamp reason or equivalent」。但 v3.5.0 PCACC-004 實作（[run_precommit_check.py:run_pcacc_004](../../artifacts/scripts/run_precommit_check.py)）對 missing timestamps 之行為為：

```python
if review_ts is None and evidence_ts is None:
    check["status"] = "skipped_with_reason_code"
    check["reason_code"] = "no_review_or_evidence_timestamp"
```

PCACC v3.5.0 policy 之 limitations 第 4 條 + run_pcacc_004 之語意：「Missing review_timestamp or evidence_generated_at returns skipped_with_reason_code, never silent pass.」即 missing → skipped_with_reason_code with explicit reason_code，**從不**靜默 pass。

兩種解讀：

- **A. 嚴格字面解讀**：expected_status 必為 `fail`；若 actual_status=`skipped_with_reason_code` 則 case fail。需要修改 runner 把 missing 改回 fail；違反 prompt §11「forbidden changes: weakening PCACC-001..004」之精神，且打破 v3.5.0 既定 policy 條款。
- **B. "or equivalent" 條款解讀**：prompt §8.6 自帶「or equivalent」leeway；v3.5.0 之 skipped_with_reason_code with explicit reason_code 為 fail-without-silent-pass 之操作等價（皆使 commit 不能視作通過）；NEG-006 之**核心保證**為「PCACC-004 absolutely never silently passes when timestamps are missing」。

對策：採 **B**。

理由：

- v3.5.0 之 skipped_with_reason_code 行為為 TASK-1026 deliverable 之既定設計，由 [precommit-check-policy.v3.5.json](../governance/precommit-check-policy.v3.5.json) limitations 條款 + [run_precommit_check.py:run_pcacc_004](../../artifacts/scripts/run_precommit_check.py) 共同證實；改 runner 違反 prompt §11 forbidden changes。
- skipped_with_reason_code with `no_review_or_evidence_timestamp` 確實阻止 commit pass（runner exit code 1 if any check status is fail；skipped_with_reason_code 雖不直接 fail，但 explicit reason_code 仍為 audit 證據，由 governance 流程介入裁決）。
- driver 之 NEG-006 pass 條件加入 `check["status"] != "pass"` 顯式驗證「runner 從不靜默 pass」。
- result JSON limitations 第 6 條 + verify artifact AC-10 + case-006 notes 三處顯式援引此條款，使 reviewer 容易追溯解讀依據。
- 此解讀為 conservative refinement：未來若 v3.5.2 / v3.6 改 runner 使 missing timestamps → fail，可重 run 本 driver 並調整 expected_status 至 `fail`；本決策不阻擋未來嚴格化。

**關鍵衝突 4（NEG-007 / NEG-008 採何種介面）**：

`run_pcacc_001..004` 不直接驗證 policy 結構（只在 main() 之 validate_policy 階段攔截）；NEG-007 / NEG-008 之 forbidden mutation 須以 `validate_policy(policy)` 為 entry point。三種選擇：

- **A. 將 mutated policy 寫入 fixture 並透過 runner CLI（`--policy <path>`）執行**：須改 driver 包 subprocess；CLI 只走 main() flow，須先有完整 fixture lifecycle 才會走到 PCACC checks；增加複雜度。
- **B. 構造 fixture lifecycle + 用 mutated policy 呼叫 run_pcacc_003**：PCACC-003 之 canonical 集合來自 policy；mutated free_text_rationale 不影響 PCACC-003；mutated 5-check 也不影響 PCACC-003 結果（PCACC-003 只看自己的 canonical 欄位）；無法直接證明 forbidden 被拒。
- **C. 直接呼叫 `validate_policy(mutated)`**：runner 之 `validate_policy()` 已含 4-check count 檢查 + free_text_rationale=False 強制；回傳 None 表通過、回傳字串表 reject reason。

對策：採 **C**。

理由：

- `validate_policy()` 是 PCACC runner 在執行 checks 前之第一道 schema gate；若 mutated policy 走到此即被拒，等於整個 PCACC pipeline 被攔下。
- 直接呼叫無需 subprocess、無需構 lifecycle、無 fixture 開銷；測試最小化。
- driver 之 NEG-007 / NEG-008 將 `validate_policy(mutated)` 之回傳字串放入 `actual_reason_code`；pass 條件比對預期字串。
- mutated policy 仍寫入 fixture 檔（`artifacts/verify/TASK-1030/fixtures/case-007-.../mutated-policy.json`、`case-008-.../mutated-policy.json`）為 evidence artifact，便於 reviewer 重現。

**關鍵衝突 5（cache pollution 防範）**：

`importlib.util.module_from_spec + spec.loader.exec_module` 之 default 行為會在 `artifacts/scripts/__pycache__/` 建立 `run_precommit_check.cpython-XYZ.pyc`；`python artifacts/verify/TASK-1030/run_pcacc_negative_tests.py` 之 default 行為會在 `artifacts/verify/TASK-1030/__pycache__/` 建立 driver .pyc。兩者皆會：

- 影響後續 QC-IMPORT-001 之 candidate 評估（雖目前 advisory，未來 strict 後易 false positive）。

- driver 第三行 `os.environ.setdefault("PYTHONDONTWRITEBYTECODE", "1")` 強化 env-level 防護。

## Reasoning

1. **artifact-first lifecycle 延續**：TASK-1023..1029 雙標 decision_class framing 已立 v3.5.0 / v3.5.1 governance pattern；本 decision 沿用 forward-compat + backward 相容設計（YAML frontmatter 用新 taxonomy `governance-pcacc-negative-test`、markdown body 用既有 `conflict-resolution`）。
2. **import-as-module 之必要性**：runner `run_pcacc_001..004` signature 第一參數即 repo_root；提供任意 fixture repo root 即可隔離真實生產樹；無須改 runner；無須維 mirror byte-identity；最小可行隔離策略；前案 TASK-1029 已驗證可行性。
3. **synthetic in-memory policy mutation 之必要性**：runner `validate_policy` signature 為純 dict 參數；無須 fixture file；real `precommit-check-policy.v3.5.json` 全程不動；mutation 採 deepcopy 確保 real policy reference 不漂移。
4. **cache 防護之必要性**：`sys.dont_write_bytecode = True`（import 前）+ `PYTHONDONTWRITEBYTECODE=1` env + `python -B` 三重保險；確保 driver execution 不留任何 `__pycache__` 或 `*.pyc`；保 QC-IMPORT-001 之 candidate baseline 純淨。
5. **PCACC-NEG-006 之 fail-without-silent-pass 等價解讀之必要性**：v3.5.0 PCACC-004 之 skipped_with_reason_code with explicit reason_code 為 prompt §8.6 之 "or equivalent" 條款下 fail-without-silent-pass 之操作等價；改 runner 為 fail 違反 prompt §11 forbidden changes；本 case pass 條件加入 `status != "pass"` 強化「never silent pass」保證。
6. **不啟用 forbidden 擴張之必要性**：NEG-007 / NEG-008 為**反向證明**（attempted activation rejected by validate_policy），**不**為**正向實作**；driver 只 mutate deepcopy，real policy reference 全程只讀；result JSON limitations 第 5 條 + decision §「Non-authorization」三處顯式聲明 PCACC active surface 嚴限四項。
7. **不 broadly modify real lifecycle artifact 之必要性**：違反 prompt §2 + decision §「Non-authorization」；fixture 採新建獨立 synthetic task IDs（TASK-9001..TASK-9006）與獨立 fixture root（`artifacts/verify/TASK-1030/fixtures/case-XXX/`），絕不與真實 TASK-XXXX 之 namespace 衝突。
8. **fixture 樹放在 `artifacts/verify/TASK-1030/fixtures/` 之必要性**：與 task 之 verify evidence 同 namespace；codex post-commit verifier 可在同一目錄一次取齊 fixture + driver + result JSON；commit clean-up 與 git tracking 皆 atomic；沿用 TASK-1029 之相同結構慣例。
9. **不執行 pytest 之必要性**：prompt §2 forbidden；pytest 之 conftest 收集 / fixture lifecycle / cache 機制皆增加非必要複雜度；driver 為 single-file Python script，可由 codex 直接 `python -B` 執行驗證。
