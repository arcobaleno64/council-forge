## Affected Gate

## Scope

Documentation/index only: human-readable closure snapshot markdown

status-semantics repair.

## Issue

The v3.5.x governance chain (v3.5.0 quality control surface
introduction through v3.5.5 golden CLI coverage with status semantics
repair) is committed and verified, but there is no single,
machine-readable closure record cross-referencing the version
chain, task groups, capabilities, protected production surfaces, and
non-authorization boundaries. Without such a record, future v3.5.6+
or v3.6 work risks silently relying on (or violating) the implicit
boundaries already in place.

## Options Considered

### Option A: Create closure snapshot and machine-readable index only (chosen)

Author a human-readable snapshot markdown plus a JSON closure index,
plus inspection evidence. No production change. No new test. No new
registry. No prior task artifact mutation. No TASK-1039+ creation.

### Option B: Bundle closure snapshot with TASK-1038 candidate execution

Reject. The prompt explicitly forbids executing TASK-1039+ work and
explicitly does not authorize TASK-1038 to execute the
golden-CLI-coverage extension or any other follow-up. Bundling would
violate the non-authorization boundary recorded by TASK-1035 /
TASK-1036 / TASK-1037 status.

### Option C: Refresh prior task artifacts to include closure metadata

Reject. The prompt explicitly forbids modification of TASK-1023..TASK-1037
lifecycle artifacts (including TASK-1037 repair artifacts). Closure
metadata belongs in a new index that references prior artifacts, not
in retroactive edits.

### Option D: Defer closure snapshot until TASK-1039+ extends coverage

Reject. The closure snapshot's purpose is to make the current state
readable before any v3.5.6+ work begins. Deferring would leave the
v3.5.x chain unindexed at the moment the v3.5.x cycle is otherwise
complete.

## Chosen Option

create closure snapshot and machine-readable index only

## Implications

- The snapshot makes the v3.5.x state readable at a single point
  without requiring readers to traverse fifteen status JSONs.
- Future v3.5.6+ or v3.6 work has an explicit non-authorization
  surface to respect; any future lifecycle that violates a recorded
  boundary becomes immediately visible by diff against the index.
- Candidate task IDs (TASK-1039..TASK-1043) recorded in the snapshot
  are advisory only; they do not constitute authorization and must
  not be used as a starting point without an explicit user prompt.
- The TASK-1037 status semantics repair (`actual_status` /
  `expected_status` versus `observed_cli_status` /
  `expected_cli_status`) is preserved in the closure narrative so
  any future golden-CLI-coverage extension inherits the corrected
  schema rather than the pre-repair conflation.
