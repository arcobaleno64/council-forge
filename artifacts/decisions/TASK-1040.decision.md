# Decision: TASK-1040

## Decision Class

governance-waiver-policy-runtime-extraction-plan

## Affected Gate

Waiver policy runtime extraction plan (no active runtime gate;
planning/index only).

## Scope

Planning-only: a runtime extraction plan markdown plus a companion
runtime extraction plan JSON plus inspection evidence over the
TASK-1039 waiver policy registry prototype. The plan defines the
safe future path to runtime consumption (activation model, runtime
loading model, fail-closed matrix, waiver selection / matching
semantics, Evidence Ref integration, golden CLI coverage
requirements, runner/template mirror preservation, backward
compatibility, rollback strategy, future TASK-1041 acceptance
criteria) without implementing any of it.

## Issue

TASK-1039 delivered a design-only waiver policy registry prototype
(`artifacts/governance/prototypes/waiver-policy-registry.prototype.v3.5.7.json`)
that consolidates waiver semantics from four committed sources but
explicitly forbids runtime consumption
(`runtime_consumption_authorized=false`, `prototype_status=design_only`,
41 `non_authorization` keys all `false`).

Before any future runtime extraction lifecycle (candidate
TASK-1041 in the TASK-1039 follow-up list) can be authorized, the
runtime path must be planned in detail: which CLI activation
shape, which fail-closed envelope, which fixture-level reason_code
surface, which preservation invariants for production runners and
template mirrors, which rollback path. Without this plan, any
future implementation lifecycle would have to design the runtime
contract under implementation pressure — exactly the failure mode
that TASK-1034 prevented for the Evidence Ref runtime extraction
(TASK-1035) and that TASK-1036 prevented for the golden CLI
coverage extension (TASK-1037).

TASK-1040 records the planned runtime path before any runtime
extraction is authorized.

## Options Considered

### Option A: Create a planning-only waiver runtime extraction plan and JSON (chosen)

Author the plan markdown and plan JSON under
`artifacts/governance/`, and the inspection evidence under
`artifacts/verify/TASK-1040/`. No production change. No new test.
No new runtime registry. No prototype mutation. No prior task
artifact mutation. No TASK-1041+ creation.

### Option B: Bundle the plan with runtime extraction (TASK-1041 implementation)

Reject. The TASK-1039 prototype carries
`runtime_consumption_authorized=false` and
`task_1040_plus_authorized=false`; the v3.5.x closure index
records `new_runtime_registry_extraction_authorized=false` and
`task_1039_plus_authorized=false` (post-TASK-1039 the closure
boundary becomes `task_1041_plus_authorized=false`); bundling
would violate three non-authorization boundaries and contradict
the prototype's explicit design-only status.

### Option C: Modify the TASK-1039 prototype JSON in place to lift `runtime_consumption_authorized` to true

Reject. The TASK-1039 prototype is a recorded attestation of
design-only state at HEAD `ff94995`; modifying its
non-authorization block would amend a prior task artifact, which
is forbidden by `task_1023_to_1038_lifecycle_modification_authorized=false`
(extended to TASK-1039 by the same logic) and by the v3.5.x
closure index `prior_task_artifact_modification_authorized=false`.

### Option D: Defer the plan until the runtime extraction task is authorized

Reject. Without a planning-time contract, the implementation
lifecycle would have to consolidate the runtime contract under
runtime pressure. The plan's purpose is to make the runtime path
readable and reviewable before any implementation begins — exactly
the role TASK-1034 played for the Evidence Ref runtime extraction.

### Option E: Promote the prototype to a runtime registry under `artifacts/governance/` (drop `prototypes/` parent)

Reject. The prototype JSON deliberately lives under
`artifacts/governance/prototypes/` to keep it out of the runner
load path. Promotion is a runtime extraction step, not a planning
step; promotion belongs to the future implementation lifecycle and
must be guarded by the activation model defined in the plan, not
by ad-hoc movement during a planning task.

## Chosen Option

create planning-only waiver runtime extraction plan

## Reasoning

TASK-1040 is planning-only.

- Runtime consumption is **NOT** authorized.
- Production runner modification is **NOT** authorized.
- Production validator/test modification is **NOT** authorized.
- Existing production governance policy modification is **NOT**
  authorized.
- Waiver prototype registry modification is **NOT** authorized.
- New test implementation is **NOT** authorized.
- Validator module split is **NOT** authorized.
- TASK-1041+ execution is **NOT** authorized.
- TASK-1023..TASK-1039 lifecycle artifact modification is **NOT**
  authorized (including TASK-1037 repair evidence, TASK-1038
  closure evidence, and TASK-1039 prototype evidence).
- PCACC-005 or any new active PCACC check introduction is **NOT**
  authorized.
- AC-to-verify coverage activation is **NOT** authorized.
- Bootstrap Prompt Skill modification is **NOT** authorized.
- v3.5 / v3.5.1 plan / manifest modification is **NOT** authorized.
- pytest / ruff / formatter / package manager invocation is **NOT**
  authorized.
- Modification of `.obsidian/`, `.omc/`, `.tmp/`,
  `.pytest-basetemp/` is **NOT** authorized.
- SRS / RTM / design spec / threat model / release note / migration
  note / user guide / runbook content generation is **NOT**
  authorized.
- The closure-index `new_runtime_registry_extraction_authorized=false`
  recorded by TASK-1038 still applies; this plan does **NOT** lift
  that boundary.
- The prototype's `runtime_consumption_authorized=false` recorded
  by TASK-1039 still applies; this plan does **NOT** lift that
  boundary.

Any future waiver runtime extraction implementation (registry
installation under `artifacts/governance/`, runner attachment via
the planned `--waiver-policy` CLI flag, golden CLI coverage of
waiver paths beyond GCLI-QUALITY-SYNC-005..GCLI-QUALITY-SYNC-006,
validator split, runtime registry expansion for the remaining RC
slices) must be separately authorized under a future lifecycle
that satisfies the plan's future TASK-1041 acceptance criteria.

Claude Code commits only allowed TASK-1040 files after
self-verification passes (inspection JSON `overall_status=pass`
and no forbidden mutation). Codex performs post-commit PASS/FAIL
verification per `agent_roles.negative_tester`.

## Implications

- The plan makes the future runtime path readable at a single
  point (markdown for humans + JSON for machines) without altering
  any production surface.
- Any future waiver runtime extraction task has an explicit
  contract source plus an explicit non-authorization surface; any
  future lifecycle that violates a recorded boundary becomes
  immediately visible by diff against the plan JSON
  `non_authorization` block.
- The plan inherits TASK-1035's Evidence Ref runtime extraction
  pattern (explicit CLI flag, default behavior unchanged,
  fail-closed envelope with stable reason_codes, runner/template
  mirror byte preservation) so future implementation has a tested
  template to follow.
- The plan does NOT promote the prototype JSON; the prototype
  remains under `artifacts/governance/prototypes/` until a future
  lifecycle authorizes promotion under the planned activation
  model.

## Expiry

Plan reflects state at HEAD `ff94995` (TASK-1039 prototype waiver
policy registry commit). Plan is not invalidated by future commits
but a future plan task may produce a refined runtime extraction
plan under a later `plan_version`.
