## Decision Class

governance-waiver-runtime-implementation-readiness-decision

## Affected Gate

Waiver runtime implementation authorization readiness (no active
runtime gate; readiness/index only).

## Scope

Decision-only: a readiness decision markdown plus a companion
readiness matrix JSON plus inspection evidence over the TASK-1040
waiver policy runtime extraction plan, the TASK-1039 waiver policy
registry prototype, and the v3.5.x governance closure index. The
package decides one of three values:

- `ready_for_separate_human_authorization`
- `not_ready_for_runtime_implementation`
- `ready_only_for_smaller_planning_followup`

The package defines the future-task implementation allowlist, hard
non-goals, and seven gates (golden CLI, Evidence Ref, runner
mirror, fail-closed, rollback, human authorization, Codex
verification) that any future implementation lifecycle must
satisfy. The package does NOT authorize implementation; even where
the readiness decision selects
`ready_for_separate_human_authorization`, a future implementation
task must still be separately and explicitly authorized by the
human maintainer.

## Issue

TASK-1040 delivered a planning-only waiver policy runtime
extraction plan
(`artifacts/governance/waiver-policy-runtime-extraction-plan.v3.5.8.md`
and `.v3.5.8.json`) that records the safe future runtime path
(activation model, runtime loading model, 24-row fail-closed
matrix, waiver selection / matching semantics, Evidence Ref
integration, 19-case golden CLI coverage requirements, runner /
template mirror preservation, backward compatibility, rollback
strategy, future TASK-1041 acceptance criteria FTC-1..FTC-15)
without implementing any of it
(`plan_status=planning_only`,
`implementation_authorized=false`,
`runtime_consumption_authorized=false`, 48 `non_authorization` keys
all `false`). Codex post-commit verification of TASK-1040 returned
PASS.

Before any future waiver runtime implementation lifecycle (e.g.
candidate TASK-1042) is authorized, an authorization readiness
decision is required. Without this readiness decision, a future
implementation lifecycle would inherit FTC-1..FTC-15 only as
informal text inside the TASK-1040 plan; with this readiness
decision, the criteria are individually scored, the implementation
allowlist is recorded, the seven gates are surfaced, and the
non-authorization boundary is repeated explicitly so that any
future lifecycle that violates a recorded gate becomes
immediately visible.

TASK-1041 records the authorization readiness decision before any
runtime implementation is authorized.

## Options Considered

### Option A: Create a decision-only readiness package (chosen)

Author the readiness decision markdown and readiness matrix JSON
under `artifacts/governance/`, and the inspection evidence under
`artifacts/verify/TASK-1041/`. No production change. No new test.
No new runtime registry. No prototype mutation. No TASK-1040 plan
artifact mutation. No prior task artifact mutation. No TASK-1042+
creation.

### Option B: Bundle the readiness decision with implementation (TASK-1042 implementation)

Reject. The TASK-1040 plan JSON carries
`implementation_authorized=false`,
`runtime_consumption_authorized=false`, and 48
`non_authorization` keys all `false`; the v3.5.x closure index
records `new_runtime_registry_extraction_authorized=false`;
bundling would violate three non-authorization boundaries and
contradict the plan's explicit planning-only status.

### Option C: Modify the TASK-1040 plan JSON in place to lift `implementation_authorized` to true

Reject. The TASK-1040 plan JSON is a recorded attestation of
planning-only state at HEAD `bbdd7ad`; modifying its
`non_authorization` block would amend a prior task artifact, which
is forbidden by `task_1023_to_1039_lifecycle_modification_authorized=false`
(extended to TASK-1040 by the same logic) and by the v3.5.x
closure index `prior_task_artifact_modification_authorized=false`.

### Option D: Defer the readiness decision until the implementation task is authorized

Reject. Without a readiness-time decision, the implementation
lifecycle would have to score FTC-1..FTC-15 under runtime pressure
and would lack a recorded gate set. The readiness decision's
purpose is to make the gate inventory readable and reviewable
before any implementation begins.

### Option E: Author a freeform readiness note without a structured criteria block

Reject. A freeform note cannot be machine-checked against
TASK-1040 FTC-1..FTC-15. The readiness matrix JSON's
`readiness_criteria` block is the load-bearing artifact: each FTC
appears as a row with `criterion_id`, `description`, `status`,
`evidence_ref`, and `blocking_if_missing` so that every future
implementation lifecycle inherits an explicit gate inventory.

## Implications

- The readiness decision makes the future authorization
  prerequisite readable at a single point (markdown for humans +
  JSON for machines) without altering any production surface.
- Any future waiver runtime implementation task has an explicit
  gate inventory plus an explicit non-authorization surface; any
  future lifecycle that violates a recorded gate becomes
  immediately visible by diff against the readiness matrix JSON
  `non_authorization` and `gates` blocks.
- The decision inherits TASK-1035's Evidence Ref runtime extraction
  pattern (explicit CLI flag, default behavior unchanged,
  fail-closed envelope with stable reason_codes, runner/template
  mirror byte preservation) so future implementation has a tested
  template to follow.
- The decision does NOT promote the prototype JSON; the prototype
  remains under `artifacts/governance/prototypes/` until a future
  lifecycle authorizes promotion under the planned activation
  model.
- The decision does NOT lift the TASK-1040 plan's
  non-authorization; the plan's
  `implementation_authorized=false` continues to apply until a
  future lifecycle that satisfies FTC-1 (explicit human
  authorization) lands.
