## Decision Class

governance-waiver-runtime-implementation

## Affected Gate

QC-SYNC-001 runtime waiver suppression surface inside
`run_quality_gates.py`. PCACC, Evidence Ref registry, validator,
QC-SCHEMA-001, QC-IMPORT-001, QC-GOLDEN-001, QC-RUFF-001 advisory
surfaces are NOT affected.

## Scope

Implementation: add an explicit `--waiver-policy <path>` CLI
argument to `artifacts/scripts/run_quality_gates.py` (and copy
the modified runner byte-identically to its template mirror at
`template/artifacts/scripts/run_quality_gates.py`). When the
flag is supplied, the runner loads a
`waiver-policy-registry/v1` registry from the explicit path,
validates it under the TASK-1040 fail-closed contract
(FC-01..FC-24), and applies its valid active unexpired waivers
to QC-SYNC-001 findings only. When the flag is absent, behavior
is byte-identical to TASK-1025 / TASK-1037 default mode.

The runtime registry schema_version `waiver-policy-registry/v1`
is distinct from the TASK-1039 prototype schema_version
`waiver-policy-registry-prototype/v1`. The prototype
schema_version is rejected at runtime load. No production waiver
registry is created under `artifacts/governance/` by TASK-1042;
the only registries that exist under TASK-1042 are isolated
fixture registries with `registry_status=runtime_test_fixture`
beneath `artifacts/verify/TASK-1042/fixtures/`.

## Issue

TASK-1041 recorded a `ready_for_separate_human_authorization`
readiness decision for a future waiver runtime implementation
lifecycle (candidate TASK-1042) along with FTC-1..FTC-15
acceptance criteria and seven gates (golden CLI, Evidence Ref,
runner mirror, fail-closed, rollback, human authorization, Codex
verification). The human maintainer (`arcobaleno`) has now
explicitly authorized TASK-1042 implementation per the prompt at
`Downloads/TASK-1042-ClaudeCode-Prompt-v3.5.10.md`.

Without TASK-1042, the QC-SYNC-001 runtime suppression surface
remains driven solely by `quality-gate-policy.v3.5.json#waivers`
(the legacy explicit-policy-waivers-array discovery mode), and
no separate runtime registry can be consumed by the runner.
TASK-1042 lands the smallest safe runtime surface so that future
waivers can be authored under an isolated registry and consumed
by `run_quality_gates.py` only when the operator explicitly opts
in via `--waiver-policy <path>`.

## Options Considered

### Option A: Explicit CLI-only `--waiver-policy <path>` in `run_quality_gates.py` (chosen)

Add the explicit CLI argument and a runtime registry loader to
`run_quality_gates.py` (root and template). Apply runtime waivers
only to QC-SYNC-001 findings. Do not modify
`run_precommit_check.py`. Do not modify production validators /
tests / governance policies. Do not promote the TASK-1039
prototype to a runtime registry. Do not implement automatic
discovery or environment-variable-only activation. The activation
mirrors TASK-1035's `--evidence-ref-policy` pattern.

### Option B: Bundle runtime waiver attachment into PCACC runner

Reject. The TASK-1041 readiness matrix records
`pcacc_runner_waiver_registry_attachment_authorized=false` and
TASK-1040 plan JSON records the same. PCACC active surface
remains four (PCACC-001..PCACC-004); attaching the waiver
registry to `run_precommit_check.py` would cross the
`pcacc_active_check_expansion_authorized=false` boundary.

### Option C: Default to the TASK-1039 prototype path when `--waiver-policy` is omitted

Reject. The TASK-1041 readiness matrix records
`runtime_registry_promotion_from_prototype_authorized=false` and
`prototype_schema_version_runtime_consumption_authorized=false`.
Defaulting to the prototype path would silently lift those
boundaries.

### Option D: Implement environment-variable-only activation (e.g. `WAIVER_POLICY=<path>`)

Reject. The TASK-1040 plan JSON records
`activation_kind=explicit_cli_only` and the TASK-1041 readiness
matrix records non-goal NG-10 (no environment-variable-only
activation). Environment-variable-only activation would obscure
the activation site and complicate audit.

### Option E: Implement automatic discovery (scan `artifacts/governance/` for waiver registries)

Reject. The TASK-1040 plan JSON records
`activation_model.no_automatic_discovery=true` and the TASK-1041
readiness matrix records non-goal NG-9. Automatic discovery
violates the explicit-CLI-only contract.

### Option F: Apply runtime waivers across all quality gates (QC-SCHEMA-001, QC-IMPORT-001, QC-GOLDEN-001, QC-RUFF-001 advisory)

Reject. The TASK-1040 plan JSON `waiver_selection_model` scopes
runtime suppression to QC-SYNC-001 (mirroring
GCLI-QUALITY-SYNC-005 / 006 anchors). Expanding the suppression
surface beyond QC-SYNC-001 would change behavior on TASK-1029
fixtures and TASK-1037 24 golden CLI cases.

## Chosen Option

implement explicit --waiver-policy support in run_quality_gates only

## Implications

- The QC-SYNC-001 runtime suppression surface has two coexisting
  modes: legacy default (driven by
  `quality-gate-policy.v3.5.json#waivers`, byte-identical to
  TASK-1025 / TASK-1037) and runtime registry-driven (driven by
  the explicit `--waiver-policy <path>` flag). Both modes can be
  active in a single run; runtime waivers are consulted before
  legacy waivers; legacy waivers fall through unchanged when no
  runtime match is found.
- Reason codes for runtime suppression carry the waiver_id and
  expires_at (`waiver_active_until:<waiver_id>:<expires_at>` for
  baseline-existing pairs;
  `post_baseline_new_pair_waiver_active_until:<waiver_id>:<expires_at>`
  for post-baseline new pairs). Reason codes for legacy
  suppression remain unchanged
  (`waivered_until:<expires_at>` /
  `post_baseline_new_pair_waivered_until:<expires_at>`).
- A future task may author a production runtime registry under
  `artifacts/governance/waiver-policy-registry.v<version>.json`;
  that authoring is out of scope for TASK-1042 and requires a
  separate decision artifact plus its own staging allowlist.
- A future repair / rollback task may revert TASK-1042 by
  removing the `--waiver-policy` argument and the runtime loader
  code path; the rollback strategy recorded in TASK-1040 plan
  JSON `rollback_strategy` (RB-1..RB-9) and the TASK-1041
  rollback gate is inheritable.
