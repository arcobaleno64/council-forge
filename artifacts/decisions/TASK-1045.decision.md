## Scope

Resolve the conflict between `docs/artifact_schema.md` v1 schema (canonical) and the v2 governance-class artifact format that has been in active use since TASK-1037 (TASK-1037..TASK-1043 task and decision artifacts; TASK-1025 and TASK-1032..1036 verify artifacts with multi-paragraph evidence). Conflict surfaced as 30+ contract-validator failures while the artifacts are themselves committed and considered authoritative governance evidence.

## Issue

Two contradictory truths exist in the repository at HEAD `0a6fb6f`:

1. The v1 schema in `docs/artifact_schema.md` (§5.1, §5.6, §5.7) declares the authoritative format for task / verify / decision artifacts. The validators `guard_status_validator.py` and `guard_contract_validator.py` enforce this v1 schema by checking required markers (`## Objective`, `## Constraints`, `# Decision Log:`, `## Issue`, `## Chosen Option`, `## Reasoning`), the canonical Decision Class taxonomy (5 values), the Affected Gate pattern (`Gate_A..Gate_E`), and the Expiry timestamp format (Asia/Taipei ISO 8601).

2. The committed governance artifacts in TASK-1037..TASK-1043 (and the multi-paragraph evidence pattern in TASK-1025, TASK-1032..1036) consistently adopt a v2 format: tasks use `## Title` / `## Description` / `## Non Goals` / `## Authorized Production Surface`; decisions carry YAML frontmatter `schema_version: decision/v2`, use `# Decision:` headlines, `## Context` / `## Decision` / `## Consequences` H2s, `governance-*` Decision Classes, "None" Affected Gates, and commit-anchored Expiry prose; verify artifacts use multi-paragraph evidence values.

Per `docs/orchestration.md` §2.2 ("以最新且合法狀態的 artifact 為準"), the latest committed artifacts win. But the v1 schema document still names the v1 format as canonical, and the validator enforces v1. The result is a 30+ artifact validator failure in main.

## Options Considered

### Option α — Artifact-side repair (rewrite TASK-1037..1043 + TASK-1025, 1032..1036 to v1 format)

Reject. v2 governance artifacts encode commit-pinned, snapshot-only, attestation-grade evidence whose H2 sections (`## Authorization Surface`, `## Context`, `## Consequences`) carry semantic load that v1's `## Issue` / `## Chosen Option` / `## Reasoning` cannot fully express. Rewriting them would drop information density and undo the deliberate evolution from the v3.5.x governance repair chain.

### Option β — Schema/validator evolution (chosen)

Validator accepts v1 OR v2 additively. v1 schema remains canonical. v2 alternatives are documented as additive options for the governance-class family (`governance-*` Decision Class). Multi-paragraph evidence parser is fixed by changing the splitter from blank-line boundary to AC-N item-start boundary, preserving v1 fallback. All Tier 1 changes mirror to `template/`.

Selected: this option preserves the v3.5.x governance evolution, restores green validation across the repo, and remains compatible with downstream terminal repos that may use either v1 or v2.

### Option γ — Quarantine via decision waivers per-task

Reject. Adds `decision_waivers` entries to TASK-1025, TASK-1032..1043 status JSONs to suppress validator failures by gate. This kicks the schema-divergence can down the road: every new governance-class artifact would need a fresh waiver, and the waiver `expires` field would force periodic rejection without solving the underlying mismatch.

## Chosen Option

Option β — Schema/validator evolution.

## Reasoning

- v2 schema represents a deliberate PDCA / double-loop learning evolution (Argyris 1977 framing in `docs/artifact_schema.md` §5.9 is itself an example of the same outward growth). The proper response to a working evolution is to absorb it into the system, not to revert.
- Keeping v1 acceptance unchanged means every artifact pre-TASK-1037 (and TASK-1044) continues to validate without modification. β is purely additive at the schema-doc and validator level.
- The blast radius is bounded: 3 Tier 1 files (`workflow_constants.py`, `guard_status_validator.py`, `docs/artifact_schema.md`) plus their `template/` mirrors. Production runners (`run_quality_gates.py`, `run_precommit_check.py`) and governance policies are untouched.
- The `governance-` prefix is a syntactically narrow extension to `DECISION_CLASSES`; it is not free-form. A non-empty subclass token is required, preventing accidental broadening of the taxonomy.
- The Affected Gate / Expiry relaxations apply only to `governance-*` classes; v1's five classes remain bound to the original strict checks.
- The verify checklist parser fix is independent of v2: it repairs a parser bug that would also affect any future v1 verify artifact whose evidence happens to span paragraphs. The legacy blank-line splitter is preserved as a fallback.

## Implications

- Future task / decision authors may continue to use either v1 or v2 format. v1 remains the recommended default for non-governance decisions because its schema is sharper.
- Future governance attestation chains (e.g. v3.5.x closure snapshots, v3.6 capability expansion records) gain first-class validator support without per-task waivers.
- Downstream terminal repos that copy `template/` after this task will inherit v2 acceptance automatically.
- Future schema evolutions beyond v2 should follow the same pattern: additive marker tuples, prefix-family Decision Classes, conditional strict checks, parser fallbacks.
- This decision creates an obligation: subsequent `docs/artifact_schema.md` revisions must keep §5.13 aligned with the validator's current v2 acceptance set.
