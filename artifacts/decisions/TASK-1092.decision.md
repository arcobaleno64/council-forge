## Issue

FB-5 (from TASK-1087 CP-4; observed ~8x across this session): Invoke-CodexAgent.ps1 treated a
SUCCESSFUL (exit 0) codex dispatch as a failure whenever the output contained a transport-error
substring (429 / Failed to fetch / ECONNRESET / RateLimitError). A code review that quotes/discusses
such tokens — or whose tool-traces echo reviewed content — spuriously tripped the retry-pattern check,
causing retry → backoff → tier escalation → "all fallback models exhausted" EXIT=1, despite valid
content. The original code matched `$RegexPattern` against `$combinedText` (stdout answer + stderr).

## Options
- Option A: scope the retry-pattern match to STDERR (`$errText`) only, not the combined stream.
- Option B: make the EXIT CODE the sole success signal — on exit 0, do NOT scan output at all;
  use RetryPatterns only to classify the backoff log on genuine (exit != 0 / thrown) failures.

## Chosen Option
**Option B** (after Option A was implemented and EMPIRICALLY DISPROVEN at the implementation layer).

## Reasoning

Option A (stderr-only) seemed sound on paper and passed plan review + impl-v1 *text* review. But the
working-tree impl-review RUN itself disproved it: the codex CLI echoes the reviewed content (the very
transport-error tokens) to STDERR too (tool traces / reasoning), so an exit-0 dispatch still matched
`$errText` and exhausted. The exit code is the only reliable signal; ANY content scan on exit 0 is
fundamentally ambiguous (a review quoting "429" is textually identical to a real 429, on either
stream). Option B trusts the contract: exit 0 = success.
