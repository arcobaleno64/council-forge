## 5. TASK-1029 Candidate Scope — QC-SYNC-001 Controlled Negative Tests

### 5.1 Objective

證明 QC-SYNC-001（source/template sync gate，TASK-1025 deliverable）確能擋下下列六種受控 violation；證明 baseline-existing drift 在不變動下保持 non-failing。

### 5.2 Negative Test Cases (planning-only; no implementation in TASK-1028 or TASK-1029-prep stage)

1. **post-baseline source-only addition**：新增 `artifacts/scripts/<new>.py` 但不新增對應 `template/artifacts/scripts/<new>.py` → 預期 QC-SYNC-001 fail with `post_baseline_new_pair` violation。
2. **post-baseline template-only addition**：新增 `template/artifacts/scripts/<new>.py` 但不新增 root 對應檔 → 預期 QC-SYNC-001 fail。
3. **post-baseline source/template drift**：新增 root + template 對偶但內容 SHA256 不一致 → 預期 QC-SYNC-001 fail with drift violation。
4. **valid unexpired waiver**：對既有 baseline-existing drift 提供合法且未過期之 decision artifact waiver（六欄齊備、`expires_at` 為未來時點） → 預期 QC-SYNC-001 pass with `waived_with_unexpired_waiver` reason code。
5. **expired waiver**：對既有 drift 提供 `expires_at` 已過時點之 waiver → 預期 QC-SYNC-001 fail with `expired_waiver_invalid` violation。
6. **baseline-existing drift remains non-failing if unchanged**：對 baseline 中已存在之 drift entry，若 root + template 兩端皆未動，預期 QC-SYNC-001 pass with `baseline_existing_drift` classification。

### 5.3 Constraints (must hold for TASK-1029)

- 所有 negative test 必須在隔離 fixture / reversible test sandbox 中執行；**不**真實寫入 repo working tree 之 template/ 或 artifacts/ 對偶區。
- 所有 fixture 必須在測試結束時被 teardown；不留持久 mutation。
- 不修改 run_quality_gates.py 之 production code path（fixture 可採環境變數或 CLI flag 形式注入；具體機制由 TASK-1029 plan 決定）。
- 不修改 quality-baseline.v3.5.json（baseline 為 immutable snapshot）。
- 不執行 broad drift remediation（即 fix existing baseline drift）；本任務僅做 negative test。
- 不擴張 QC-SYNC-001 邏輯之 production behavior。

### 5.4 Out of Scope (TASK-1029)

- 不執行 QC-SCHEMA-001 / QC-IMPORT-001 / QC-GOLDEN-001 之 negative test（屬 future v3.5.1 candidate 或 v3.5.2）。

## 6. TASK-1030 Candidate Scope — PCACC Controlled Negative Tests

### 6.1 Objective

證明 PCACC（pre-commit cross-artifact consistency check，TASK-1026 deliverable）之四項 strict checks 確能擋下下列八種受控 violation；證明 PCACC 不超出 v3.5.0 之四檢查（即不誤啟用 AC-to-verify coverage activation）。

### 6.2 Negative Test Cases (planning-only)

1. **missing lifecycle artifact**：commit 一份 task 卻缺 plan / decision / verify / status 之任一 → 預期 PCACC-001 fail with `lifecycle_artifact_missing`。
2. **malformed Evidence Ref**：verify artifact 之 `## Evidence Refs` 含非 repo-relative path / 含非法字元 / 為空字串 → 預期 PCACC-002 fail with `evidence_ref_format_invalid`。
3. **missing Evidence Ref when required**：assurance_level=`production` 之 verify artifact `## Evidence Refs` 為空 → 預期 PCACC-002 fail with `evidence_ref_missing`。
4. **non-canonical owner/reviewer reference**：verify artifact 之 reviewer 欄位採非 canonical id（如英文全名、暱稱、未在 owner registry 之 id） → 預期 PCACC-003 fail with `owner_reviewer_non_canonical`。
5. **review_timestamp earlier than evidence_generated_at**：verify artifact 之 reviewer timestamp 早於 evidence (test result / build log) 之生成時間 → 預期 PCACC-004 fail with `review_before_evidence`。
6. **missing timestamp with no reason code**：verify artifact AC item 之 `timestamp` 欄位缺失且無 `reason_code` → 預期 PCACC-001 / PCACC-004 之一 fail。
7. **forbidden free_text_rationale field**：verify artifact 含 `## Reasoning Faithfulness` 或 `## Belief State` 或 `## Free Text Rationale` 等被 v3.5.0 PCACC scope 顯式排除之 section（TASK-1026 decision §3 之 forbidden surfaces） → 預期 PCACC fail with `forbidden_free_text_rationale_section`。

### 7.1 Objective

### 7.2 Target Modules (characterization scope)

- `artifacts/scripts/workflow_constants.py`
- `artifacts/scripts/run_red_team_suite.py`
- `artifacts/scripts/test_guard_units.py`

### 7.3 Readiness Criteria (must hold before any v3.6 module split)

1. **stable golden CLI coverage**：golden CLI corpus 覆蓋上述模組之主要 entry point CLI；連續 N 次（N 由 TASK-1031 plan 決定）run 之輸出 SHA256 穩定。
2. **behavioral characterization coverage**：對每模組之核心 public function / class，補上 characterization tests（記錄當前行為，**不**試圖修正設計缺陷）。
3. **source/template sync green or waived with expiration**：QC-SYNC-001 對上述模組為 pass 或具有未過期 waiver。
4. **known responsibility map**：每模組之責任區段（functions / classes 之分工）寫成 explicit map（markdown table），供 v3.6 split 對照。
5. **no broad refactor before characterization**：v3.5.1 期間禁止對上述模組做超出 characterization 範疇之 refactor（typo / format / 註解修正可，邏輯 / 結構修正不可）。

- 既有 unit tests 與 red-team drills 應**共用** `artifacts/test/legacy_verify_corpus/` 中之 fixtures（與 docs/artifact_schema.md §1.2 對齊）。

## 8. TASK-1032 Candidate Scope — Policy Registry Extraction Design Decision

### 8.1 Objective

評估 **policy registry extraction** 是否應先於 validator module split；若是，定義 design constraints 與 schema；若否，記錄拒絕之依據。本任務僅做 **design decision**，**不**抽 policy registry。

### 8.2 Decision Criteria (must be defined by TASK-1032)

- **policy data vs execution logic 之邊界**：哪些常數（regex、checklist、severity table、reason code enumerations、allowed values）屬於 policy data，可移入 JSON registry；哪些屬於 execution logic（control flow、I/O、subprocess invocation、error handling），必須留在 Python。
- **JSON registry shape**：若採 JSON registry，schema 是否需含 versioning（schema_version、effective_from、supersession）；是否需與既有 quality-gate-policy.v3.5.json / precommit-check-policy.v3.5.json / artifact-obligation-matrix.v3.5.json 共享 schema 風格。
- **Python residual**：哪些常數因 type / serialization / circular dependency 等原因必須留在 Python；列出明確標準。
- **schema validation requirements**：JSON registry 之載入是否需 schema validation；schema validation 失敗時是否阻止 runner 啟動。
- **source/template sync implications**：JSON registry 是否須加入 source/template paired files；若是，QC-SYNC-001 baseline 是否需更新；若否，存放位置之治理規則。
- **backward compatibility with existing validators**：抽 policy registry 後，`workflow_constants.py` 等既有匯入點之相容性策略；是否須留 transitional shim；shim 之 expiration policy。
- **rollout staging**：若決議抽，預期分幾階段；每階段之 verification gate 為何。

### 8.3 Constraints (must hold for TASK-1032)

- TASK-1032 為 **design decision only**；output 為 decision artifact（內含 chosen option 與 rejected options）+ 對應 task / plan / verify / status lifecycle。
- TASK-1032 **不**抽 policy registry。
- TASK-1032 **不**修改 `workflow_constants.py` 或任一既有 validator。
- TASK-1032 之 decision 為 v3.6 policy registry implementation 之 input；v3.6 任務若不引用本 decision，不得啟動 implementation。

### 8.4 Out of Scope (TASK-1032)

- 不抽 policy registry。
- 不執行 module split。
- 不修改 v3.5.0 governance policy。
- 不修改既有 runner 或 validator。

## 9. v3.5.1 Defer / Forbid Statements

### 9.1 Validator Module Split — Deferred to v3.6

v3.5.1 期間**禁止**執行 validator module split。理由：

- v3.5.0 缺乏 negative test 證明 control 真能擋；v3.5.1 之 TASK-1029 / TASK-1030 補此證據。
- v3.5.0 缺乏 characterization coverage；v3.5.1 之 TASK-1031 補此覆蓋。
- v3.5.0 缺乏 policy registry design decision；v3.5.1 之 TASK-1032 補此決策。
- 缺前述任一條件即執行 split，refactor 風險高（FIND-30 之 monolith maintainability risk 之原因即在缺乏 characterization）。
- 與 v3.5 manifest version_split_rule 對齊：`v3.6: structural evolution after behavior is characterized: validator split, policy registry extraction, PCACC AC coverage, validator output schema versioning; requires v3.5.x characterization tests and gates to remain green for at least one release cycle`。

### 9.2 Policy Registry Extraction Implementation — Deferred to v3.6

v3.5.1 期間**禁止**執行 policy registry extraction implementation。TASK-1032 僅做 design decision。理由同 §9.1。

### 9.3 Document Generation — Out of Scope

v3.5.1 期間**禁止**生成 SRS / RTM / design spec / threat model / release note / migration note / user guide / operation runbook 之任何**內容**檔案。AOM matrix 之 forbidden_generation 規則持續適用。

### 9.4 PCACC Scope Creep — Forbidden

v3.5.1 期間 PCACC 嚴限 v3.5.0 之四檢查；任何擴張須 separate decision artifact 與 v3.5.2 或更後 follow-up task 顯式授權。

### 9.5 New Governance Plane — Forbidden

v3.5.1 期間**禁止**創建：

- standalone waiver registry。
- standalone style debt registry。
- policy registry（design decision 不算 implementation）。
- 新 governance plane（AC-to-verify coverage、reasoning faithfulness、belief-state audit、SAVeR markdown report）。
