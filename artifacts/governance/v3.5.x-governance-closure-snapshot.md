## 7. TASK-1037 repair summary

The v3.5.5 deep closure review failed on a single schema/contract
issue: `actual_status` carried negative CLI outcome values (`fail`,
`exit_2_load_failed`, `exit_2_invalid_task_id`) that conflated two
distinct semantics — golden case assertion status and observed
runner CLI outcome.

The 2026-05-05 repair (commit `05083d1`) separates the two semantics
in the per-case schema:

- **Golden assertion status** — `expected_status` / `actual_status`
  now strictly carry the golden case assertion status. Allowed
  values: `pass`, `skipped_with_reason_code`, `advisory`. After
  repair, `actual_status` carries `pass` for all 24 implemented
  cases and never `fail` or `exit_2_*`.
- **CLI outcome status** — `expected_cli_status` /
  `observed_cli_status` are added to encode the runner / harness
  CLI outcome. Allowed values: `pass`, `fail`,
  `skipped_with_reason_code`, `advisory`, `exit_2_load_failed`,
  `exit_2_invalid_task_id`. Former negative observations
  (`fail` x10, `exit_2_load_failed` x4, `exit_2_invalid_task_id` x1)
  are preserved under `observed_cli_status`; positive observations
  (`pass` x9) appear for the success-path cases.

Negative CLI outcomes such as `fail`, `exit_2_load_failed`, and
`exit_2_invalid_task_id` belong in `observed_cli_status`, not in
`actual_status`. Any future golden-CLI-coverage extension must
inherit this corrected schema rather than the pre-repair conflation.

Repair scope (only TASK-1037 evidence touched): harness
(`run_golden_cli_coverage.py`), result JSON
(`golden-cli-coverage-result.json`), case manifest
(`golden-cli-case-manifest.json`), verify markdown
(`TASK-1037.verify.md`), and status JSON
(`TASK-1037.status.json#repair_history,repair_result`). Production
runners, production validators, governance policies, prior task
artifacts, and TASK-1038+ scope were not touched by the repair.
