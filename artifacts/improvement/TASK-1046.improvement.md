## What Actually Happened

Rewrite script approach was the right lever — collapsed ~40 individual file edits into a single deterministic pass with full audit trail. Sentinel rename via `git mv` preserved git history. Most surprising: many files I expected to have project-name references didn't (e.g. README.md ended up unchanged because the bulk-rewrite found no remaining instances after prior tasks; START_HERE / GEMINI / CODEX likewise). The rewrite script's "unchanged" entries are themselves evidence that prior workflow tasks had already minimised name dependence.

## Steps That Felt Redundant

- TASK-1046 lifecycle artifacts (task / research / plan / decision) were drafted before TASK-1047 was triggered; the drafts had to be left mid-flight while CI was repaired. Not redundant per se, but the context-switch cost was real.

## Error-Prone Steps

- Inline Python heredoc bash commands triggered escape-sequence errors (single backslash in re-pattern). Switching to a `.tmp/` script file resolved cleanly.
- The post-commit GitHub rename + remote URL update is manual and easy to forget; documented explicitly in this artifact's §6 to mitigate.

## Surprises / Mismatches

- README.md / README.zh-TW.md / OBSIDIAN.md / START_HERE.md / GEMINI.md / CODEX.md showed zero diffs — prior tasks had migrated them to project-name-agnostic content.
- The `template/.github/repository-profile.json` was already aligned to the new content (no diff), suggesting an earlier tactical sync.

## Template / Workflow Fix Candidates

- Document the rename runbook in `docs/lightweight_mode_rules.md` or a new `docs/rename_runbook.md` as a forward-facing reference for the next project rename.
- Consider whether `.consilium-source-repo` style sentinels should hold a content payload instead of being just a filename, so future renames are content-only and don't require `git mv`.

## Next Time Default

For project renames: write a single rewrite script in `.tmp/`, declare the path whitelist explicitly, verify with SHA-256 prefix table, sentinel-rename via `git mv`, then run validators. The post-GitHub-rename steps are mechanical and should be scripted as a follow-on operation list.
