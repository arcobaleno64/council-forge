## 1. What Happened

CI `Workflow Guards` had been red on master for 9 days (since TASK-1005, commit 24956035299, 2026-04-26). Every push since (TASK-1037..TASK-1045 plus chore commits) failed CI on the same 36 unit-test failures plus a `--cov-fail-under=100` coverage gate that no commit could meet because two CLI runners (`run_quality_gates.py`, `run_precommit_check.py`) sat at 0% unit-test coverage by design (they are exercised via subprocess in red-team / fixture flows, not unit tests). User flagged the red CI when reviewing recent runs. TASK-1047 repaired the 36 failures in four categories (mock fakes accept `timeout` kwarg, status fixtures declare `assurance_level`, task fixtures include `## Assurance Level` H2, UTF-8 wrap tests call `init_streams()` directly), updated `.coveragerc` to omit the two CLI-only runners with rationale, and lowered `--cov-fail-under` from 100 to 90 (per task constraint allowance; not below 90).

## 2. Why It Was Not Prevented

Three system-level gaps:

1. **Test-fixture central helpers were not updated when production contracts evolved.** TASK-1008 introduced strict `assurance_level` enforcement; the central `_make_full_status` / `_modern_status` / `_setup_valid_done_tree` / `_build_task_artifact` helpers were not migrated. Each subsequent fixture-using test inherited the omission. No guard raised an alarm at TASK-1008's time because the failures only manifested in CI, and the CI gate was not blocking merges.
2. **CI gate was set to an unattainable threshold (`--cov-fail-under=100`) with no integration-test plan to cover the CLI-only runners.** The 100% gate was aspirational rather than operational; once the two runners landed at 0%, the gate locked CI red.
3. **Successive PRs (TASK-1037..TASK-1045) merged without CI green** because the working agreement implicitly tolerated failing CI as long as local-validator-green held. This eroded the CI signal value over 9 days.

## 3. Failure Classification

Premortem failure (TASK-1008 / TASK-964 / `run_command` signature change each made a contract change without auditing test fixtures and CI gate feasibility) + workflow gap (no policy that "CI red on master is a stop-the-line event").

## 5. Preventive Action (System Level)

- **Fixture-helper invariant**: any new strict-mode field added to artifact validators must be added simultaneously to the central test-fixture builders (`_make_full_status` / `_modern_status` / `_setup_valid_done_tree` / `_build_task_artifact`). Document this rule in `docs/artifact_schema.md` §5.1 Adapter section and in `.github/memory-bank/workflow-gates.md` if present.
- **CI gate feasibility**: any future increase to `--cov-fail-under` threshold must be paired with an integration-test plan that demonstrates current code can meet the threshold. New CLI-only runners require either unit-test coverage or explicit `.coveragerc` omit at the same time as the new file lands.
- **CI-red stop-the-line**: future rule — if `Workflow Guards` is red on master, the next task's first acceptance criterion is "restore CI green" before any other change.
- Document CI-red watch as a periodic hygiene check (e.g. weekly `gh run list --limit 20` review).

## What Actually Happened

Investigation surfaced that all 36 failures fell into clear categories with central-helper fixes; no individual test rewrites needed for the bulk. The CI gate at 100% was the harder question: the two CLI runners that drag coverage to 77% would require an integration-test investment that's out of scope for a CI-repair task. Pragmatic compromise: omit them and lower threshold to 90%, document the trade-off, and propose the integration-test follow-up.

## Steps That Felt Redundant

- Initial fixture inspection one-by-one before realising the central helpers (`_make_full_status` / `_modern_status` / `_setup_valid_done_tree` / `_build_task_artifact`) were the lever. After locating the central fixtures, the bulk of repairs collapsed to ~5 edits instead of ~20+ individual test patches.

## Error-Prone Steps

- Status JSON edits — overwrote the file once with a duplicate `{` heading because a partial Edit confused the boundary; recovered with full Write rewrite.
- Plan's `Files Likely Affected` extraction silently dropped paths starting with `.` (e.g. `.coveragerc`, `.github/...`) and paths annotated with parenthesised suffixes (e.g. `(this lifecycle)`); fix is to wrap all paths in backticks for explicit recognition.

## Surprises / Mismatches

- The `init_streams` UTF-8 wrap tests assumed module reload would trigger the wrap; production design moved init_streams to be called only from `main()`, breaking the test's premise. Test rewrite to call `vcs.init_streams()` directly matches the new design.
- Coverage gate at 100% had been failing since TASK-1005 but no commit had attempted to either reduce the threshold or add the missing tests. The unattainable threshold had become a no-op signal.

## Template / Workflow Fix Candidates

- Add a guard validator check that flags any new `--cov-fail-under` value or threshold change in `.github/workflows/*.yml` when the corresponding `.coveragerc` doesn't have the supporting omits; this would catch threshold-vs-coverage drift at PR time.
- Document the `Files Likely Affected` extraction quirk (leading-dot paths, parenthesised suffixes) in `docs/artifact_schema.md` §5.3 Plan section so future authors wrap paths in backticks by default.

## Next Time Default

- Wrap every path in `Files Likely Affected` with backticks; leading-dot files are otherwise silently dropped from the validator's drift check.
