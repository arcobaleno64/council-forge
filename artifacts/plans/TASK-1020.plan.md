## Risks

R1
- Risk: v3.3 plan 文件不存在於倉中，但 prompt 與 decision 文字假設其存在；若未誠實揭露，後續代理將以為 v3.3 為實檔基線並嘗試讀取，引發 cascade 誤判
- Trigger: decision artifact 之 supersedes 欄位指向不存在 path；後續代理 grep `consilium-fabri-governance-repair-plan-v3.3.md` 為 0 hits 而誤以為 v3.4 之 supersession 主張不成立
- Detection: 任一後續 task（如 TASK-1005）之 research / decision artifact 含 `unable to locate v3.3` 字樣；或 guard validator 對 supersedes path 報 `path does not exist`
- Mitigation: decision artifact 之 `## Issue` 與 `## Reasoning` 顯式記載「v3.3 並未落為實檔，supersession 對象為概念基線」之事實；v3.4 plan 文首亦複述此事實；後續代理據此繼續而不再嘗試讀取 v3.3
- Severity: blocking

R2
- Risk: v3.4 plan 內某處 `plan_version` 仍殘留 `v3.2` 或 `v3.3`（複製貼上舊文之故），重蹈 v3.3 之 self-validation bug；TASK-1020 verify 因 grep 而判 fail，或更糟，verify 漏檢而通過
- Trigger: 撰寫 v3.4 plan 時引用既有 schema 例如 `decision/v2`、`governance-repair-manifest/v1` 等之相鄰處，誤把 plan_version 寫成 schema_version 之版本字串
- Detection: `grep -nE 'plan_version.*v3\.[023]' consilium-fabri-governance-repair-plan-v3.4.md` 有任何 hit
- Mitigation: v3.4 plan 撰寫完成後立即 grep `plan_version` 與 `v3.[023]` 兩字串；verify artifact 之 AC-3 evidence 為此 grep result；發現殘留即修正
- Severity: blocking

R3
- Risk: decision artifact 採雙標（YAML frontmatter 用 v3.4 新 taxonomy `governance-plan-supersession`，markdown body 用 `conflict-resolution`）後，[guard_status_validator.py](../../artifacts/scripts/guard_status_validator.py) 或 [guard_contract_validator.py](../../artifacts/scripts/guard_contract_validator.py) 未來若加 strict YAML frontmatter 檢查，可能將此 frontmatter 視為 unknown schema 而 fail
- Trigger: validator 升級加 frontmatter 嚴格檢查，且未先 whitelist `decision/v2` schema
- Detection: validator run 報 `unknown schema_version: decision/v2`
- Mitigation: decision artifact 之 `## Reasoning` 顯式記載此雙標策略與相容性目的；validator 升級時須先讀此 decision；若未來 strict 模式需要，TASK-1007（RACI Auditor v2）會處理 schema validation 升級
- Severity: non-blocking

R4
- Risk: manifest 之 `depends_on` DAG 設計錯誤（如循環、孤兒、與 v3.4 plan 文中執行序不一致），致後續代理依 manifest 跑出與 plan 文字不同之執行流
- Trigger: 撰寫 16 條 entry 時複製貼上致某 entry 之 depends_on 指向自身或下游
- Detection: 對 manifest 做 DAG 拓撲排序（以後手工或 future validator）發現循環；或人工讀 plan 文字之 §「執行序」與 manifest 對照不符
- Mitigation: 撰寫 manifest 時逐條對照 prompt label 順序；verify artifact 之 AC-14 evidence 含完整 16 條 entry 之 depends_on 列表，並標記每條為「線性鏈：前一 prompt → 後一 prompt」
- Severity: non-blocking

R5
- Risk: 撰寫 v3.4 plan 與 lifecycle artifact 過程中 token / context 不足以完整覆蓋 user prompt 之全部需求（16 prompts × schema × resume policy），致部分章節缺漏；verify 階段始發現需回頭補
- Trigger: v3.4 plan 文件 token 量超出單次 Write tool 能力，或 plan 文字精簡至遺失必要欄位
- Detection: verify artifact 之 AC-7 / AC-8 / AC-10 / AC-11 任一 evidence 找不到對應章節
- Mitigation: v3.4 plan 採章節 + 子章節結構，每 prompt 之必要欄位以 bullet list 而非散文呈現；分批 Write（先骨架後補體）；verify 前以 grep 抽核每 AC 對應章節 anchor
- Severity: non-blocking
