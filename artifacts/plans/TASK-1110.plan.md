## Risks

R1
- Risk: `guard_contract_validator.py` 之 `validate_allowed_gemini_models()` 現行 regex `\bgemini-[a-z0-9.\-]+\b` 專為 `gemini-x.y-name` 格式設計，遷移後 model 字串變為 `"Gemini 3.5 Flash (Medium)"`（含空格、括號、大寫），若僅更新 `ALLOWED_GEMINI_MODELS` 資料而不改寫 regex 本身，validator 將對新字串零匹配，等同靜默停止執行 allowlist 檢查（validator 顯示綠燈但實際未檢查任何內容）
- Trigger: 完成遷移後執行 `guard_contract_validator.py --root .`，若比對邏輯仍是舊 regex
- Detection: 於測試 fixture 中刻意插入一個不在 allowlist 內的錯誤 model 字串（如 `"Gemini 1.0 Flash"`），確認 validator 仍會回報錯誤而非靜默通過；此為「驗證 validator 本身仍在把關」的 regression test，需另補一條 negative test case
- Mitigation: 改寫 `validate_allowed_gemini_models()` 為對 `ACTIVE_GEMINI_POLICY_FILES` 逐檔內容做精確集合比對（例如抽取雙引號或反引號包住的候選字串後與 `ALLOWED_GEMINI_MODELS` 集合比對），而非沿用舊 regex 微調；新增至少一條 negative test 證明錯誤字串仍會被攔截
- Severity: blocking

R2（**獨立質疑後修正**：原始版本誤判失敗模式，已依實測修正範圍）
- Risk: 現行 wrapper 成功判定為 `$lastExitCode -eq 0 -and -not ($combinedText -match $RegexPattern)`（`Invoke-GeminiAgent.ps1:362`），任何非 0 exit code 本就會觸發重試（不受 `$RetryPatterns` 是否命中影響，原始 R2 之「第一層 tier 失敗即直接回報整體失敗」判斷有誤，已修正）。實際風險為：(a) agy 成功回傳文字若恰好包含 `429`/`400 Bad Request` 等子字串會被誤判為失敗，因比對對象是全部 combined output 而非僅 stderr；(b) agy 目前無已知之容量/速率限制專屬錯誤格式可用於判斷「值得 backoff 並晉升 tier」，本次研究僅驗證成功路徑
- Trigger: (a) agy 正常回覆內容中偶然出現數字字串巧合命中 `$RetryPatterns`；(b) agy 在實際 dispatch 中遇到容量限制、速率限制或伺服器端錯誤（無法在本次研究階段人為穩定重現）
- Detection: Coding 階段需以可控方式人為觸發至少一種 agy 失敗情境（例如刻意傳入不存在的 `--model` 觀察錯誤格式），將觀察到的實際 stderr/stdout 內容與新 `$RetryPatterns` 逐一核對；另需一條測試以「回覆文字含數字 429」之正常成功案例驗證不會被誤判為失敗
- Mitigation: 若無法窮舉 agy 所有錯誤類型，`$RetryPatterns` 比對範圍限縮為僅比對 stderr（而非 combined stdout+stderr），降低正常回覆內容誤觸發之機率；容量/速率限制之 tier 晉升邏輯若找不到 agy 專屬信號，改採「任何失敗一律晉升下一 tier」之較保守寬鬆策略
- Severity: blocking

R3
- Risk: 本次「agy 1.1.1 修復 bug 導致 6 月失敗」之結論為高可信度推論而非 100% 證實（見 research artifact Uncertain Items）；若歷史失敗真正成因是其他因素（如 consumerOAuth 登入狀態），遷移後之 wrapper 未來仍可能重演「exit 0 但輸出為空」的靜默失敗，且因 agy 舊版曾有此 bug，即使目前版本已修，仍不能排除未來版本回歸或其他路徑（如 sandbox 模式）出現同類行為
- Trigger: 任何一次 agy dispatch 回傳 exit code 0 但 stdout 為空白或僅含空白字元
- Detection: wrapper 內建防禦性檢查：`$Output.Trim().Length -eq 0` 且 `$ExitCode -eq 0` 時，強制視為失敗並觸發重試/降級，而非視為成功
- Mitigation: 無論歷史成因是否 100% 查明，本次遷移都必須加入此項「空輸出視為失敗」的防禦性檢查作為 defense-in-depth，不依賴對 agy 內部 bug 是否徹底修復的信任
- Severity: blocking

R4（**獨立質疑後修正 mitigation**：改為樂觀預設，避免不必要的雙軌測試）
- Risk: 現行 wrapper 刻意採 stdin 餵入 prompt（而非 `-p` 參數）以避開 Windows cmd.exe 對多行/長字串的截斷問題；agy 同樣提供 `-p`/`--print`，但其在 Windows 下對長/多行 prompt 之行為未經驗證，且 agy 1.1.2 changelog 提及「當 stdin 被 piped prompt 佔用時，透過 controlling terminal 讀取 OAuth 授權碼」，暗示 agy 的 headless 模式對 stdin 佔用有特定假設，與現行 wrapper 之 stdin-only 設計可能衝突。獨立質疑已初步以互動模式（非 headless `-p`）測試 stdin 餵入多行文字，exit 0 且內容看似完整保留，但屬初步觀察非確認（未針對 headless `-p` 路徑測試）
- Trigger: Coding 階段以 500 字以上或多行 prompt 測試 agy 呼叫
- Detection: 撰寫一個要求「逐字複誦以下內容」的測試 prompt，比對 agy 實際回傳內容是否為完整文字而非截斷版本
- Mitigation: 樂觀預設——先僅測試 stdin 形式；若通過即視為確認完成，不需要額外測試 `-p` 形式；僅在 stdin 實測失敗（截斷或掛住）時才改測 `-p`，並於 decision artifact 記錄此一設計變更之驗證依據
- Severity: non-blocking

R5
- Risk: `DISALLOWED_GEMINI_FRAGMENTS`（現行封鎖 gemini-2.0/2.5 字串）遷移後若未決定去留即遺留，會變成無意義的死條件（agy 字串本就不含這些片段，規則恆真但無實際作用）；若逕自刪除又未記錄理由，日後 rule lifecycle audit 盤點可能誤判為「無理由移除既有規則」
- Trigger: Coding 階段編輯 `guard_contract_validator.py` 時決定此清單去留
- Detection: 盤點時檢查 `DISALLOWED_GEMINI_FRAGMENTS` 是否仍含已與新 allowlist 無關聯之舊字串，且 decision artifact 是否記錄去留理由
- Mitigation: 由於 `ALLOWED_GEMINI_MODELS` 已是封閉集合精確比對（R1 之修復方式），舊有 disallow-list 對封閉集合比對而言是多餘的雙重保險；Coding 階段明確決定「移除並在 decision artifact 記錄理由（Chesterton's Fence：封閉 allowlist 已涵蓋其防禦目的，非無理由移除）」或「保留作為額外防禦層並更新內容」，兩者擇一並記錄，不得靜默遺留死條件
- Severity: non-blocking
