## Background

v3.4 治理修復鏈於 TASK-1016（end-to-end smoke test）已封閉（commit `2403c98`、`dba0ebf`），threat model rebuild v3.4 由 TASK-1012 完成。v3.4 已穩定，但浮現五項新治理需求，使 v3.5.0 之引入成為必要：

1. **FIND-29 source/template sync fragility**：v3.4 之 source/template pair 仍仰賴人工 `template/` 同步，缺少 baseline-aware exact-sync 與 drift waiver expiration。
2. **FIND-30 validator and test monolith maintainability risk**：`artifacts/scripts/guard_status_validator.py`（70x hot path）與其 unit tests 已長至單檔 monolith；refactor 風險高，須先量測 baseline 再決定是否拆檔。
3. **FIND-31 multi-model style and behavior drift**：Claude / Codex / Gemini 之 style、CLI 輸出、JSON schema、import-time side effect 缺乏跨模型一致性 gate；多模型協作下治理證據易飄移。
4. **FIND-32 cross-artifact consistency blind spot**：v3.4 之 verify floor 與 contract validator 為單 artifact 等級；缺少 pre-commit cross-artifact 結構一致性檢查（PCACC），如 task / plan / decision / verify timestamp 順序、evidence ref 對應。
5. **FIND-33 artifact obligation ambiguity**：v3.4 對「該 task 該不該有 X artifact」採隱性慣例；缺少 obligation matrix 約束；artifact bloat 風險高（過度生成 SRS、RTM、design spec）。

v3.5.0 之治理目標為「最小可驗證一致性控制面」，**非**「validator 真拆檔」、**非**「文件內容生成」、**非**「bootstrap prompt skill 入 core repo」。版本拆分原則：

- v3.5.0 — controls before refactor（baseline-aware quality gates、minimal PCACC、artifact obligation matrix）。
- v3.5.1 — refactor only after controls are green（小範圍 validator split candidate）。
- v3.5.2 — maintenance policies after evidence accumulates（waiver registry、retention，僅當數據顯示需要）。
- v3.6 — structural evolution after behavior is characterized（validator split、policy registry extraction、PCACC AC coverage）。

本 plan-introduction lifecycle 同時須處理「[注意] Numeric task ID order is not execution order」原則：v3.5.0 execution order 由 manifest 決定，非 task ID 數字順序。
