## Closure Repair (2026-05-05)

The v3.5.5 deep closure review failed on a single schema/contract issue:
`actual_status` carried negative CLI outcome values (`fail`,
`exit_2_load_failed`, `exit_2_invalid_task_id`) that conflated two distinct
semantics — golden case assertion status and observed runner CLI outcome.

This repair separates the two semantics in the per-case schema:

- `actual_status` / `expected_status` now strictly carry the golden case
  assertion status. Allowed values: `pass`, `skipped_with_reason_code`,
  `advisory`. After repair, `actual_status` carries `pass` for all 24
  implemented cases (since every case has `pass=true`) and never `fail`
  or `exit_2_*`.
- `observed_cli_status` / `expected_cli_status` are added to encode the
  runner / harness CLI outcome. Allowed values: `pass`, `fail`,
  `skipped_with_reason_code`, `advisory`, `exit_2_load_failed`,
  `exit_2_invalid_task_id`. Former negative observations (`fail` x10,
  `exit_2_load_failed` x4, `exit_2_invalid_task_id` x1) are preserved
  under `observed_cli_status`; positive observations (`pass` x9) appear
  for the success-path cases.

Case-level `pass` boolean retains its original meaning: true iff the
observed CLI behavior matched the golden contract (exit code, JSON
subset, reason_code, stderr, expected_cli_status).
