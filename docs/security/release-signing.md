# Release Signing — key lifecycle & trust anchor (SSDF PS.2)

> **映而不疊 / map-don't-recreate**: this is the single source of truth for how council-forge's
> release surface is **cryptographically signed and verified**. The mechanism is plain `gpg`
> (no re-implemented crypto). `release_gate.py` stays an **offline structural** gate; the REAL
> cryptographic check is the native `gpg --verify` step in
> [`.github/workflows/security-scan.yml`](../../.github/workflows/security-scan.yml)
> (`release-integrity` job). Discovery pointers live in
> [`SECURITY.md`](../../SECURITY.md), [`.well-known/security.txt`](../../.well-known/security.txt),
> and the cadence index [`security_cadence.md`](../security_cadence.md).

SSDF **PS.2** = *"Provide a Mechanism for Verifying Software Release Integrity"* — make
integrity-verification information available to acquirers (PS.2.1). council-forge's release
surface is the propagated `template/` SSOT snapshot, published as a content-addressed manifest at
[`.well-known/release-manifest.json`](../../.well-known/release-manifest.json) (generated by
`snapshot_manifest.py`). PS.2.1 lists three notional examples: **Example 1** = publish
reproducible cryptographic hashes (already shipped — this is why PS.2 is `partial`); **Example 2**
= sign with a key whose public half acquirers can trust; **Example 3** = periodically review the
signing process (rotation / revocation / key protection). This document specifies the Example 2/3
mechanism so it is **implemented and tested**, while being explicit that flipping PS.2 to
`covered` depends on **operator actions** this repository deliberately does not take here.

## 1. Mechanism — detached signature over the manifest

The manifest is signed with a **detached, ASCII-armored** signature, so the manifest's bytes and
schema are unchanged (no embedded-signature schema churn):

```bash
# Sign (operator, with the release-signing private key in the operator's own keyring):
gpg --detach-sign --armor \
    --output .well-known/release-manifest.json.asc \
    .well-known/release-manifest.json

# Verify (CI and any acquirer, offline, against the published public key):
gpg --verify .well-known/release-manifest.json.asc .well-known/release-manifest.json
```

A signed-tag variant is equivalent for the git release surface:

```bash
git tag -s vX.Y.Z -m "council-forge release vX.Y.Z"   # sign
git tag -v vX.Y.Z                                      # verify
```

Verification binds to the **signer**, not merely "some good signature". CI parses the GnuPG status
stream and requires the `VALIDSIG` fingerprint to equal the pinned anchor — see §3.

## 2. Key management (NIST PS.2.1 Example 2/3)

| Dimension | Policy |
|---|---|
| **Generation** | `gpg --quick-generate-key "<release identity>" ed25519 sign` (or `rsa4096`). Generate on a trusted, offline-capable operator machine — **never** in CI, **never** committed. |
| **Storage (out of repo)** | The **private** key lives only in the operator's GnuPG keyring, or hardware (YubiKey / smartcard / HSM). It is **never** committed to this repo and **never** placed under `.well-known/`. For an automated signer, use OIDC keyless (Sigstore) or an encrypted CI secret — not a key file in the tree. |
| **Rotation** | Rotate on a defined cadence (e.g. annually) and immediately on suspected compromise. Publish the new public key + its fingerprint out-of-band, update `EXPECTED_SIGNING_FINGERPRINT`, then retire the old key. Overlap windows are documented in the release notes. |
| **Revocation** | Generate a revocation certificate at key-generation time and store it separately. On compromise, publish the revocation, rotate (above), and re-sign current releases with the new key. |
| **Protection** | Passphrase-protected at minimum; hardware-backed preferred. The revocation certificate and any backup are stored separately from the working key. |
| **Periodic review (Example 3)** | The signing process — key validity, fingerprint pin correctness, rotation/revocation readiness — is reviewed on the security cadence (see [`security_cadence.md`](../security_cadence.md) → *Release Integrity*). This is the Example-3 "periodically review" obligation, not a one-time setup. |

## 3. Publication & trust anchor

1. The **public** key is published (armored) at
   [`.well-known/release-signing.pub`](../../.well-known/release-signing.pub) **by the operator**.
   It is a *public* key, safe to commit — but it is the operator's act, paired with step 2.
2. The key **fingerprint** is the trust anchor. CI pins it via the
   `EXPECTED_SIGNING_FINGERPRINT` environment variable in the `release-integrity` job. The
   native-verify step:
   - imports the published public key into an **isolated** keyring (`GNUPGHOME=$(mktemp -d)`);
   - **refuses to run** against an unpinned key (`test -n "$EXPECTED_SIGNING_FINGERPRINT"`);
   - captures the GnuPG status stream and **binds the `VALIDSIG` fingerprint to the pinned
     anchor** — so a good signature from *some other* imported key (e.g. an attacker key appended
     to the bundle) does **not** pass.
3. The operator must obtain the fingerprint to pin from an **out-of-band** channel the acquirer
   independently trusts (the project's signed release notes, a keyserver + web-of-trust, a
   separately-hosted page) — **not** from the same commit that introduces the signature.

## 4. Honest ceiling & residual risk

**This mechanism is implemented and tested, but PS.2 stays `partial` — not `covered`.** The
load-bearing parts of `covered` are **operator actions**, not code:

- generating a real signing key and protecting it (§2);
- producing a real signature over the published manifest (§1);
- publishing the public key **and** pinning the out-of-band-published fingerprint (§3);
- performing the first real verification and the ongoing rotation/revocation/review (§2).

This repository keeps `no-push` and **does not** perform these steps, so it does **not** flip PS.2.
See `docs/ssdf-mapping.md` (PS.2 footnote) — status is **`mechanism-implemented
(operator-action-dependent)`**.

**Residual (the load-bearing honesty):** a fingerprint pinned **inside this repo** is only as
trustworthy as the repo's own integrity — an attacker who controls a commit can change the pin,
the public key, and the signature together, and the self-referential check would still pass. Real
**publisher** trust requires the fingerprint to reach the acquirer through an **independent**
channel (out-of-band), which is the operator's act under §3. The CI pin defends against
*post-publication tampering of the manifest* given a trusted pin; it does **not** by itself
establish *who* the publisher is.

**No key in the repo.** No **private** key is ever generated for, committed to, or stored in this
repository (the lint asserts the tree carries no `PRIVATE KEY` material and no private key files
under `.well-known/`). The end-to-end test in `artifacts/scripts/test_release_signing.py`
generates a **throwaway** key in a temporary `GNUPGHOME` purely to exercise the sign→verify→tamper
logic, then discards it — it is never a publisher identity and is never persisted.
